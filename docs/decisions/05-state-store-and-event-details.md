# ADR 05 — State, store, controlled values and event details

| | |
|---|---|
| Status | accepted (2026-10-17) |
| Project | Blazix.Primitives |
| Decides | whether the store/selector model is ported; how controlled/uncontrolled values are exposed in Blazor; the shape of the event-details object and the reason set; two project-wide constraints (no boxing; .NET 11 / C# 15 with union types) |
| Affects | UTL-STA-01..36, UTL-ALG-03/04; PSH-STA-01..46, PSH-ALG-*; EVD-API-01..13, EVD-STA-01..10, EVD-EVT-01..27, EVD-ALG-01..11, EVD-EDGE-01/02; every component's controlled prop pairs and `on*Change` callbacks; RND-ALG-07 (amends ADR 02) |

## Context

Base UI holds plain controlled/uncontrolled values for simple components (`useControlled`, EVD-ALG-08) and a `ReactStore` for every popup family and the floating layer: one immutable record, listeners notified synchronously in subscription order with the nested-write rule UTL-ALG-03, `Object.is` equality, selectors with arguments, reactive reads that re-render only on change, a non-reactive context bag, and prop-to-store sync helpers (UTL §4.2). The popup store has 18 common fields, eleven selectors and 46 STA requirements; handles expose a stack of attached stores or an inert fallback store (PSH-STA-34..40). Ordering is observable (EVD-ALG-04, PSH-STA-44). Change callbacks receive `(value, details)` where `details` is one mutable object carrying `reason`, the native event, the trigger, `cancel()`, `allowPropagation()` and live accessors (EVD-ALG-01), shared along child-then-parent chains (EVD-EVT-04).

Blazor facts: a `CascadingValue` whose value changes re-renders every subscriber; a fixed one re-renders none, so parts must subscribe and re-render themselves (UTL §8.2, and the old port's slider pitfalls). `ParameterView.TryGetValue` reports whether a parameter was supplied, which gives "controlled iff supplied at first render" exactly. `@bind-Open` expands to `Open` plus `OpenChanged`. Store notifications run on the renderer's synchronization context.

The user added two constraints during this decision: **minimal to no boxing** anywhere the port controls allocation, and **.NET 11 / C# 15**, using union types. C# 15 facts (Microsoft docs, 2026-09): a compiler-generated `union` is a struct storing `object?`, so it boxes value-type cases; the non-boxing access pattern (`HasValue`, `TryGetValue(out T)`) on a hand-written `[Union]` struct avoids that; runtime support exists from .NET 11 Preview 5 and parts of the proposal are still unimplemented.

## Decision

### 1. Store (option ST1)

`Store<TState>` and `ComponentStore<TState>` are ported per UTL-STA-07..27: an immutable state record class, ordered listeners with the UTL-ALG-03 nesting rule (a nested write runs its own full pass and aborts the outer one), `Update(state => state with { … })` and typed `Set<TValue>` accessors, `NotifyAll`, `Subscribe`, `Observe`, named selectors `Func<TState, TValue>` and `Func<TState, TArg, TValue>`, and a non-reactive context bag of typed fields. Equality is `Is<T>`: value types and `string` by value, every other reference type by reference, matching `Object.is`; store fields that are C# records are compared by reference, never structurally. `PartBase` gains a selector subscription: one subscription per part, every selection re-evaluated per notification, `StateHasChanged` only when a selection changed (UTL-STA-25/27). Prop-to-store sync (`useSyncedValue`, `useSyncedValues`, `useControlledProp`) runs in `OnParametersSet`; UTL §8.1 sanctions this because only the store is touched. The store is cascaded fixed (`IsFixed = true`). The store is used exactly where Base UI uses it (UTL §4.2 "Used by"); simple components keep plain fields plus `Controlled<T>` implementing EVD-ALG-08 and EVD-STA-01..06. Handles port as `PopupHandle<TPayload>` with the attached-store stack, pointer listeners and the inert fallback store (`NullStore`, PSH-STA-34..40); detached triggers subscribe to the pointer.

### 2. Controlled values in Blazor (option A2)

Every value exposes `Value`, `ValueChanged` (`EventCallback<T>`) and `DefaultValue` (names per component: `Open`/`OpenChanged`/`DefaultOpen`, `Checked`/…), plus `OnValueChange: EventCallback<ValueChangeEventArgs<T>>` carrying the details. Controlled iff `Value` was supplied at first `SetParametersAsync` (`ParameterView.TryGetValue`), fixed for the component's lifetime (EVD-STA-01). Request sequence (EVD-ALG-03/04 unchanged, with one added step): compute → `OnValueChange(args)` → if `IsCanceled` stop → `ValueChanged(value)` → commit when uncontrolled → follow-up side effects. `@bind-Value` therefore works, and `ValueChanged` fires only from the component's own request path, so EVD-STA-06 holds. The two-callback shape is a documented superset of Base UI's one callback.

### 3. Event details and reasons (option R1)

`ChangeEventDetails` is a mutable class: `Reason` (enum), `Event` (the snapshot record of ADR 04), `Trigger` (record of trigger id and `ElementReference`), `Cancel()`, `AllowPropagation()`, live `IsCanceled`/`IsPropagationAllowed`. `OpenChangeEventDetails : ChangeEventDetails` adds `PreventUnmountOnClose()`. Component extensions are subclasses (`TabsChangeEventDetails.ActivationDirection`, `SliderChangeEventDetails.ActiveThumbIndex`, `HighlightEventDetails.Index`). `GenericEventDetails` carries `Reason` and `Event` only (EVD-API-02). One object flows through chained callbacks (EVD-EVT-04/09). The callback argument is `readonly record struct ValueChangeEventArgs<T>(T Value, ChangeEventDetails Details)`; `EventCallback<ValueChangeEventArgs<T>>` delivers it without boxing. Reasons are one `enum BaseUIEventReason` with the 36 members of EVD §3.5 and a `ToLiteral()` extension producing the kebab-case literal; per-callback subsets remain documentation (EVD §4.3.7). Dev warnings EVD-EDGE-01/02 are kept behind a debug switch.

### 4. Project-wide constraints

* **No boxing where the port controls it.** Generic store, selectors and listeners; enum reasons; typed `EventCallback<T>`; the pipeline's attribute bag is a typed entry list with a hand-written non-boxing `[Union] struct AttributeValue(string, bool, EventCallback, Delegate)` emitted through `RenderTreeBuilder`'s typed `AddAttribute` overloads; state projection is source-generated (amends ADR 02). Boxing forced by Blazor's own contracts is accepted and minimised: `CaptureUnmatchedValues` is `Dictionary<string, object>`; `IJSObjectReference.InvokeAsync` takes `object?[]`, so twins pass one options record per call rather than scalars.
* **.NET 11 and C# 15.** Union types are used for reference-typed alternatives: `Render` as `RenderFragment | RenderFragment<RenderProps<TState>>`, `ClassValue`/`StyleValue` as `string | Func<TState, string?>`, `Anchor` cases that are reference types. Value-typed alternatives (`double | double[]` for Slider, anything with `ElementReference`) use hand-written `[Union]` structs with the non-boxing access pattern, or stay as two typed parameters. `closed` hierarchies are used where exhaustive matching over a library-defined set helps (details subclasses). Targeting a preview runtime is accepted; the fallback for any union feature that slips is the two-parameter shape of ADR 02.

## Consequences

* ADR 02 is amended (see its Amendments section): projection by source generator; union-typed single parameters where cases are reference types, with the Razor-binding verification item below.
* A `Controlled<T>` helper and the store library are the first implementation deliverables after the pipeline; every component doc's §4 can cite UTL/PSH/EVD IDs unchanged.
* Consumers who use `@bind-Value` and also need `reason` or `cancel()` subscribe to both callbacks; the docs state the order.

## Verification items

* The Razor compiler binds `class="x"` / `Render="@fragment"` / `ClassValue="@func"` to a union-typed `[Parameter]` (implicit union conversion through component attribute binding), on the .NET 11 preview SDK. Not testable on this machine today (SDK 10.0.301 installed). **Verified 2026-10-20 (SDK 11.0.100-rc.2.26504.105, csc 5.12.0-1.26504.105, language version 15.0 by default, no feature flag): yes, with limits** — `Render="@fragment"` and `Render="@typedFragment"` bind to a declared `union RenderValue<TState>(RenderFragment, RenderFragment<RenderProps<TState>>)`; `ClassValue="x"` and `ClassValue="@func"` bind to `union ClassValue<TState>(string, Func<TState, string?>)` (the Razor compiler emits a C# string literal for a quoteless attribute value when the parameter type is a union with a `string` case, an observed rule to re-check at each SDK bump); `class="x"` still reaches the unmatched bag beside `ClassValue`. Not bound: the child-content element form `<Render>…</Render>` (RZ10012), inline lambdas and method groups without a cast to the case delegate type (CS1660, CS1503), and generic type inference through a union conversion (CS0411). A declared union stores one `object` field, so value-type cases box (24 bytes per construction) while reference-type cases do not; a hand-written `[Union]` struct with `HasValue` and `TryGetValue(out T)` never reads `Value` and allocates nothing; `default(U)` has `Value == null` and a switch over the case types throws `SwitchExpressionException` at run time, so a union-typed `[Parameter]` must be declared nullable. Finding recorded on [issue 10](https://github.com/JakeMurrayDev/Blazix.Primitives/issues/10) (spike `spikes/union-binding/`, deleted on close per ADR 14 §3); the gaps feed the checklist of the fourth item below.
* Whether component parameters bind case-insensitively (`class` to a parameter named `Class`). **Verified 2026-10-18 (SDK 10.0.301): yes** — `<Part class="x" />` compiles to `AddComponentParameter(1, nameof(Part.Class), "x")`. Consequences: a part that declares a parameter named `Class` or `Style` captures the consumer's plain attribute (it no longer reaches the unmatched bag), so the single union-typed `Class`/`Style` parameters of §4 are viable once union binding is verified on the .NET 11 SDK; until then parts must not name any parameter `Class` or `Style`, and ADR 02 P1's bag channel stands.
* `EqualityComparer<T>.Default` specialisation for value types inside `Is<T>` does not box on the WebAssembly runtime (interpreter and AOT). **Verified 2026-10-20 by measurement on the interpreter (SDK 11.0.100-rc.2.26504.105, Debug, no AOT): it does box.** `tests/browser/harness.spec.ts` "@verifies ADR-05/3" (two titles) with the `allocation` fixture, 100,000 comparisons per scenario through `GC.GetTotalAllocatedBytes`: `EqualityComparer<T>.Default.Equals` allocates 32 bytes per comparison for `int`, `long`, `double` and `bool`, 48 for `Guid` and 96 for a two-field `readonly record struct`, the same whether reached through a generic `Is<T>` or with `T` fixed at the call site; it allocates nothing for an enum, a nullable enum or a string, and `a == b` and `IEquatable<int>.Equals` allocate nothing. The assertion as the item states it is kept in the suite as a Playwright expected failure, so it turns red the day the interpreter stops boxing; the second title pins the measured profile. AOT is not measured (stated as by inspection in the issue). Consequence for §2's `Is<T>`: decided the same day, see Amendments 2026-10-20 "`Is<T>` on the WebAssembly interpreter" (the generated `ShallowEquals` avoids `EqualityComparer<T>`; the generic `Is<T>` keeps it and accepts the interpreter cost); [issue 11](https://github.com/JakeMurrayDev/Blazix.Primitives/issues/11) closed.
* Union features listed as not yet implemented in the C# 15 proposal do not include anything the parameter shapes above rely on; re-check at each preview. **Verified 2026-10-20 (SDK 11.0.100-rc.2.26504.105, csc 5.12.0-1.26504.105): nothing the narrowed shapes of Amendments 2026-10-20 rely on is missing** — the checklist is the amendment "from M0 Track 2 (issue 12)" below (one row per feature, re-run at every `global.json` change); its gaps (no lambda, method-group or lifted conversion to a union, no inference through a union conversion, `closed` types implicitly abstract) touch only shapes the union-binding amendment already dropped or workarounds it names. Finding recorded on [issue 12](https://github.com/JakeMurrayDev/Blazix.Primitives/issues/12) (probes `spikes/union-features/`, deleted with the M0 Track 2 pull request per ADR 14 §3).
* The form controls participate in a cascaded `EditContext` without changing `Form` (Amendments 2026-10-22): registration, notification, name default and message mapping hold on both render modes, and the expression parameter with `FieldIdentifier.Create` passes the trim and AOT analyzers. Milestone M2 ([issue 76](https://github.com/JakeMurrayDev/Blazix.Primitives/issues/76)); permanent L2 tests per control tagged `[Trait("Verifies", "ADR05-5")]` and one L4 title per render mode tagged `@verifies ADR-05/5`. **Verified 2026-10-23 (M2; [issue 76](https://github.com/JakeMurrayDev/Blazix.Primitives/issues/76) closed by M2 tracks 7–8, the last control to land):** every M2 form control given its expression parameter registers its `FieldIdentifier`, notifies the cascaded `EditContext` of every committed change, defaults its name to the identifier's field name and, inside a `Field.Root`, shows the context's messages through the field's external errors; without a context or an expression the parameters are inert. L2 (`Verifies ADR05-5`): `FieldControlEditContextTests` and `InputEditContextTests` (track 1), `SwitchFieldTests` (track 4, PR 95), `CheckboxFieldTests` (track 5), `CheckboxGroupFieldTests` (track 6), `RadioGroupEditContextTests` (track 8). L4, both render modes: `field.spec.ts` and `radio-group.spec.ts` "@verifies ADR-05/5 participates in a cascaded EditContext", `switch.spec.ts` "@verifies ADR-05/5 a switch bound in an EditForm notifies the EditContext and shows its validator's message" (PR 95). The trim and AOT probe (PR 88) reported no IL2xxx or IL3xxx diagnostic with `FieldIdentifier.Create` in place.

## Considered options

* Plain C# state with cascading snapshots everywhere (re-render storms on list popups; PSH-STA restated ad hoc); stores everywhere including Switch (machinery Base UI does not use).
* Literal controlled API without `@bind` support (consumers write the two-way update by hand).
* Per-callback reason enums mirroring the TypeScript unions (about thirty overlapping enums and a generic details hierarchy that shared mechanisms cannot create without knowing the component); string constants (no exhaustiveness, typos compile).

## Amendments

**2026-10-18, from the second-pass review (settles field §16 Q13, input §16 Q3, autocomplete §16 Q2, toast §16 manager shape, FFI §10 Q9's FLD-STA-12 item).**

1. **Controlled mode is fixed at the first parameter set for every part**, including `Field.Control`, `Input` and `Autocomplete`, whose Base UI implementations re-decide on every render and tolerate switching (FLD-STA-12, INP-API-01, AUT-API-01/EDGE-01). The switching clauses are relaxed for the port; supplying or removing `Value` after the first parameter set raises the same development-time warning as EVD-EDGE-01/02. No test exercises switching.
2. **One exception to the request sequence of §2**: for a request whose source is a native text edit on an uncontrolled text control (`input` events on Combobox/Autocomplete inputs, Field.Control, Input, NumberField, OTP slots), the commit proceeds regardless of `Cancel()`, because the browser has already changed the DOM and reverting typed text would be new behaviour; `Cancel()` still suppresses the follow-up effects Base UI suppresses (AUT-EVT-02 and its Combobox counterpart stay as written).
3. **Toast manager shape** (TST-API-10): `ToastManager` is a class exposing the same methods as `createToastManager()` (add, update, close, promise) and a subscription event usable outside the component tree; it is not a `Store<TState>`. `Toast.Provider` takes a manager as a parameter or creates its own, and the equivalent of `useToastManager` is the provider's cascaded instance.

**2026-10-20, two corrections from M0 Track 2 (issue 32; chosen by the user the same day).** (1) §3's claim that `EventCallback<ValueChangeEventArgs<T>>` delivers the argument "without boxing" holds only when no component receives the callback. Through a component receiver, which every consumer callback has, Blazor's `IHandleEvent.HandleEventAsync(EventCallbackWorkItem, object?)` boxes the struct (32 bytes) and its own dispatch adds about 32 bytes more, a cost a `string` argument pays too; a class argument would cost the same, so the `readonly record struct` stays and the L1 allocation budget pins both numbers (0 bytes without a receiver, about 66 bytes through one). (2) `createSelector` and `createSelectorMemoized` (UTL-STA-29..33, UTL-ALG-04) are deferred: no component of Base UI v1.9.0 consumes them (UTL §1), §1's named selectors `Func<TState, TValue>` and `Func<TState, TArg, TValue>` cover their role (UTL §8.2), and they are ported the day a component or a re-pin (ADR 15) needs them.

**2026-10-20, `Is<T>` on the WebAssembly interpreter (M0 Track 3, issue 11; chosen by the user the same day).** The third verification item's hope does not hold on SDK 11.0.100-rc.2: on the WebAssembly interpreter `EqualityComparer<T>.Default.Equals` allocates for value types (32 bytes per comparison for `int`, `long`, `double` and `bool`, 48 for `Guid`, 96 for a record struct), whether called directly or through the generic `Is<T>`, and allocates nothing for enums, nullable enums, strings, the `==` operator and a direct `IEquatable<T>.Equals` call; CoreCLR allocates nothing in every case. Decision: the store's hot path avoids the generic comparison. The `ShallowEquals` member of every store state record is source-generated with type-specific comparisons (`==` for primitives, enums and value types that define it; ordinal `string.Equals`; reference equality for every other reference type, records included; `IEquatable<T>.Equals` for a value type without `==`), so a notification compares every field without allocating on either runtime. The generic `Is<T>` behind `Set<TValue>` and the selectors keeps `EqualityComparer<T>.Default` and accepts the interpreter cost for its one comparison per write; the harness pins the profile with an expected-failure Playwright test that turns red when the platform changes, and the cost is re-measured at .NET 11 GA and under AOT in the M5 measurement (ADR 16 §B). The no-boxing constraint of §4 reads "where the port controls it" for exactly this case. *Amended 2026-10-23 (design point R8 of M2 tracks 7–8, settled by the orchestrator 2026-10-23 under the user's no-boxing rule from the M0 grilling, the origin of §4 and BLZX2005; the choice ADR 08 Amendments 2026-10-22 deferred to the Radio probe):* the primitives' branches were added after the Radio probe, in which `int` boxed 48 B per comparison on the interpreter. `Is<T>`, and through it `StrictEquals<T>`, compares `bool`, `char`, the integer types, `nint`/`nuint`, `decimal` and their nullable forms with `==` through `Unsafe.As`, as the floating-point branches do, so they allocate nothing on either runtime (`radio-group.spec.ts` "port: the value comparisons of a radio allocate nothing for a string, an enum, a record class, an int and a nullable int on the interpreter"). Other value types still use `EqualityComparer<T>.Default`, so records still box there: a two-field record struct costs 416 B per round of the Radio probe, pinned by "port: the value comparisons of a radio box a record struct on the interpreter".

**2026-10-20, enforcement in the build (M0 track 5, [issue 52](https://github.com/JakeMurrayDev/Blazix.Primitives/issues/52)).** §4's no-boxing bullet and the two rules of the union-binding amendment are build errors from the analyzers project (ADR 09). `BLZX2005` rejects three things in library code: a union (a declared `union`, or a struct marked `[Union]` or implementing `IUnion`) converted to `object` or an interface anywhere, Blazor's `object` contracts included; any other value type converted to `object` or an interface, except into Blazor's own `object` contracts, which are allow-listed by symbol (the `object` value of `RenderTreeBuilder.AddAttribute` and `AddComponentParameter`, the argument of `AddMultipleAttributes`, the `Invoke*` argument arrays of `IJSRuntime` and `IJSObjectReference` with their in-process interfaces and the extension methods on them, and a value stored into a dictionary of `string` to `object`, the unmatched bag's type); and `Enum.ToString`, `Enum.HasFlag`, `Enum.Equals(object)`, `Enum.GetValues` and `Enum.GetNames`. Calibrated on `main`: 9 hits with and without the allow-list (no library code boxed at an allowed site). Three were fixed (the two `ToLiteral` exceptions passed the enum as the actual value; the twin attach path boxed the `ElementReference` one call before the interop arguments). Six are suppressed with their reason, because a platform contract forces the box: the interface members of `AttributeList`'s struct enumerator (three), `AttributeValue.Value` for `IUnion` (two), and `EventCallback.Equals(object)` in the render pipeline's handler collection, which boxes once per part handler per render because Blazor's `EventCallback` has no typed equality. A value-type operand of a string concatenation whose type overrides `ToString` is not reported, because the compiler calls `ToString` instead of boxing it; an enum or a struct without its own `ToString` is still reported. The rule does not see an unconstrained type parameter converted to `object`, nor a struct receiver boxed by a call to an `object` member it does not override. `BLZX2006` rejects a `[Parameter]` or cascading parameter whose type is a union and is not declared `U?`. The allow-list, the six suppressions, the concatenation case and the two unseen cases are what the track recommended and the user chose the same day ([pull request 56](https://github.com/JakeMurrayDev/Blazix.Primitives/pull/56)). Removing the per-render `EventCallback` box is [issue 57](https://github.com/JakeMurrayDev/Blazix.Primitives/issues/57). All of them are listed in `src/Blazix.Primitives.Analyzers/CONTEXT.md`.

**2026-10-22, the form controls inside Blazor's `EditForm` (M2 planning; chosen by the user the same day).** `Form` is Base UI's form and stays its own: it cascades no `EditContext`, takes no `Model`, and its validation is Field's (`Validate`, `Errors`, the validation modes). The controls are cross-compatible with Blazor's form stack: inside an `EditForm`, or any ancestor that cascades an `EditContext`, a control takes the cascaded `EditContext` (an optional cascading parameter) and an expression parameter after Blazor's convention (`ValueExpression : Expression<Func<T>>?` beside `Value` on `FieldControl`, `Input`, `RadioGroup<TValue>` and `CheckboxGroup`; `CheckedExpression : Expression<Func<bool>>?` beside `Checked` on `SwitchRoot` and `CheckboxRoot`), which `@bind-Value` and `@bind-Checked` supply. With both present the control (1) builds its `FieldIdentifier` once per parameter set and calls `NotifyFieldChanged` on every committed change, so `DataAnnotationsValidator`, `ValidationMessage` and `EditForm`'s submit callbacks work as with the built-in inputs; (2) defaults its `name` to the identifier's field name (`FieldIdentifier.FieldName`, such as `Email`) when no `Name` is given, whereas Blazor's `InputBase` renders the formatted member path (`Model.Email`) for static server-side form posts, which the port's interactive parts do not serve (corrected the same day); and (3) inside a `Field.Root`, feeds the context's validation messages for its identifier into the field's external-error slot on `OnValidationStateChanged`, so `Field.Error` shows them and `data-invalid` reflects them, cleared and raised again as the validator reports (the external-error rules FFI-FRM-25/26 apply; Field's own `Validate` and modes are unaffected). Without an `EditContext` or without the expression the parameters are inert and nothing changes. No requirement document covers this behaviour, so this note is its contract and the fifth verification item above holds its tests (ADR 14 §3). Track 1 (Field) builds the shared internal participation helper and probes it under the trim and AOT analyzers before the control tracks add their parameters. Considered and declined: `Form` as an `EditForm` or with a `Model` (two validation models in one form; it re-opens FFI's requirements), and no integration in M2 with an adapter as a follow-up (the user chose participation for the controls).

**2026-10-26, `Equality.SameValueZero<T>` (M3 track 6, [issue 105](https://github.com/JakeMurrayDev/Blazix.Primitives/issues/105); settled by the orchestrator 2026-10-25, M3 plan "Settled").** `internal static bool SameValueZero<T>(T left, T right)` sits in `Store/Equality.cs` beside `Is<T>` and `StrictEquals<T>`. It is JavaScript's SameValueZero, the comparison of `Array.prototype.includes`: `Is<T>`, except that `0` equals `-0` for `double`, `float`, `Half` and their nullable forms, while `NaN` still equals `NaN`. Every other type goes through `Is<T>`, so R8's primitives allocate nothing and records compare by reference. Accordion's membership test (an Item is open when the Root's value contains its identity, ACC-STA-04) uses it; the single-mode check (ACC-STA-05) and the removal (ACC-STA-06) use `StrictEquals<T>`, which keeps the `NaN` asymmetry of ACC-EDGE-10. Loops over the list call the helpers directly, never `Contains` or LINQ, which box on the interpreter and compare records structurally. Tested by `tests/Blazix.Primitives.Tests/Store/EqualityTests.cs` ("SameValueZero: NaN equals NaN and -0 equals 0", "SameValueZero: the primitives allocate nothing").
