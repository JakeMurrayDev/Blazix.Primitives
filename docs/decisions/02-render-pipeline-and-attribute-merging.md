# ADR 02 — Render pipeline, element substitution and attribute merging

| | |
|---|---|
| Status | accepted (2026-10-17) |
| Project | Blazix.Primitives |
| Decides | how `render`, `className`/`style` functions, handler chaining with `preventBaseUIHandler()`, state data attributes, DOM handles and generated ids map onto Blazor; whether one shared implementation satisfies the conformance obligations RND-DOM-36..49 |
| Affects | RND-STR-01..09, RND-API-01..11, RND-STA-01..03, RND-DOM-01..33, RND-DOM-36..49, RND-EVT-01..13, RND-ALG-01..15, RND-EDGE-01..09; UBT handler-merging notes (UBT-EVT-01..03); EVD-API-11, EVD-EVT-26/27 |

## Context

Every Base UI part turns public parameters, a state object and part-supplied attributes into exactly one host element through one internal function (`useRenderElement`, RND-ALG-01), which is also public as `useRender`. The function supports two substitution forms (a *substitute element* that is cloned with merged attributes, and a *substitute callback* that receives the merged attribute set), class and style parameters that may be functions of state, a fixed merge precedence (RND §2.1), handler chaining with a per-dispatch veto, state-to-`data-*` projection, DOM-handle fan-out and server-stable ids. The conformance suite (RND-DOM-36..49) runs against every part.

Blazor facts that shaped the decision, verified where marked:

* Attribute splatting never merges; when `@attributes` and an explicit attribute collide, the attribute written last in the markup wins (verified, Microsoft docs). Class and style are therefore the part's job to merge before emission.
* A `RenderFragment` is an opaque delegate; there is no `cloneElement`. `RenderTreeBuilder` is public, has a public constructor and `GetFrames()` (verified, API docs), so a fragment can be rendered into a scratch builder and its frames read and re-emitted through the same public API.
* A consumer's `@onclick="H"` on a part lands in the `CaptureUnmatchedValues` bag as a boxed `EventCallback<MouseEventArgs>`; Razor emits event attribute names in lowercase. Each element's handler receives its own deserialized `EventArgs` instance, so a flag on the instance is invisible to a handler on an ancestor element. `EventArgs` carry no `target` and no `preventDefault()`.
* Blazor has no `useId` and no way for a component to learn its tree position. Prerender and interactive activation are two renders in two DI scopes.
* The old port (Blazix.BaseUI) used a child component `<RenderElement>` inside every part with a callback-only `Render`; its slider notes record a race between the parent's first render and the child's element reference, and its handler rule ran the consumer's callback after the internal handler, inverting RND-EVT-02.

## Decision

1. **Both substitution forms are offered (option B).** `Render` accepts a plain `RenderFragment` whose root is cloned (the *substitute element*), and `RenderFunction` accepts a `RenderFragment<RenderProps<TState>>` that receives the merged attribute bag, the state object and the child content (the *substitute callback*). Blazor cannot type one parameter as either, so the two parameters together are Base UI's `render`; supplying both is a development-time error.
   The element form is implemented by **frame rewriting**: the fragment is rendered into a scratch `RenderTreeBuilder`; its root element frame, attribute frames (including `EventCallback` values, `@ref` capture frames and `@key`) and child frames are read; the pipeline re-emits the root element with attributes merged per RND-ALG-02 (substitute attributes win, substitute class first, substitute style keys win, substitute handlers run first), preserves the consumer's capture frame and key, adds the part's own element reference capture, and re-emits the children frame by frame (text, markup, region, element, component with parameters, captures, named events, render modes). A root that is a component frame receives the merged attributes as its parameters, which is how a Blazix part or a consumer component accepting unmatched values nests (RND-STR-07, RND-DOM-43); such a component must forward the merged `id` so the part's JavaScript can locate the host element.
2. **Class and style have two channels each (option P1).** The plain `class`/`style` strings arrive through the unmatched bag; `ClassValue`/`StyleValue` are `Func<TState, string?>` parameters. On the consumer's side the string comes first, then the function result. Order overall is RND-DOM-14/15: substitute class, consumer string, consumer function, part classes. Style is parsed into declarations (split on `;` outside parentheses and quotes) and merged by property name with first-seen order kept, so RND-DOM-16 holds as a literal string.
3. **Handler chaining and veto (option V1).** The part registers the single real handler for each event on the host element and invokes the chain itself: substitute handler, consumer handler, part handler. The veto is `e.PreventBaseUIHandler()` / `e.BaseUIHandlerPrevented()`, extension methods on `EventArgs` backed by a `ConditionalWeakTable`; the per-dispatch scope of RND-EVT-04 follows from Blazor creating a fresh instance per dispatch. A consumer handler in the unmatched bag is any key starting with `on` whose value is an `EventCallback`, `EventCallback<T>` or delegate; name casing is irrelevant (deviation from RND-ALG-13/RND-EVT-13, where lowercase `onclick` was an ordinary attribute, because Razor lowercases event names). The cross-part case of EVD-EVT-27 (a part converts Enter/Space to a click and an enclosing part must not handle the same key) uses a *consumed flag* on the ancestor-provided context the enclosing part already reads, set by the inner handler and read-and-cleared by the outer one, which Blazor dispatches next. `preventDefault` and `stopPropagation` are not on the C# surface; they are JavaScript policy (ADR 01, ADR 04).
4. **Pipeline shape (option S2).** One static function implements RND-ALG-01/02/05/06/07/08 and the frame rewrite against a `RenderTreeBuilder`. Library parts derive from `PartBase<TState>`, which owns the state object, the unmatched bag, `ClassValue`/`StyleValue`, `Render`/`RenderFunction`, `Enabled` and the element reference, and calls the static function from `BuildRenderTree`; parts are C# classes, not `.razor` files. The public `useRender` equivalent is a `RenderElement<TState>` component over the same static function with the parameters of RND §3.2 (`Render`, `State`, `StateAttributesMapping`, `Props`, `Enabled`, `DefaultTagName`); `MergeProps` is public over RND-ALG-02. One component instance per part; `Enabled = false` renders nothing (RND-DOM-25).
   Default projection of the state object to `data-*` (RND-ALG-07) is cached reflection over the record's public properties, trimming-safe via `[DynamicallyAccessedMembers(PublicProperties)]`, restricted to own properties of primitive type (RND §10 Q4). Custom mappings (`transitionStatusMapping`, `collapsibleOpenStateMapping`, the forty component-specific ones) are hand-written.
5. **Generated ids (option I1).** `AddBlazixPrimitives()` registers a scoped id generator; every part that may need an id draws `base-ui-<n>` at first render in render order, whether or not the consumer supplied one, so RND-DOM-28/30/31 hold exactly. RND-DOM-29 holds whenever the prerender and interactive passes render the same tree in the same order; divergence (streaming rendering, data that differs between passes, roots activating out of document order) produces a different id at activation, which in Blazor is an attribute change, not a failure. The unprefixed exceptions of RND-DOM-27 are collapsed: all generated ids carry the `base-ui-` prefix (no Base UI test pins the bare form, and bare numeric ids are poor CSS targets).

One shared implementation therefore satisfies RND-DOM-36..49 for every part; the per-part conformance run exists to catch a part that bypasses or misconfigures the pipeline.

## Requirements relaxed or withdrawn for the port

| ID | Disposition |
|---|---|
| RND-DOM-19, RND-DOM-32 ("an explicitly `undefined` value on a later source also replaces the earlier value") | not expressible: the Razor compiler omits a frame for a `null` attribute value, so only present attributes participate in the merge |
| RND-DOM-20..24 (DOM handles) | the part exposes `Element` (`ElementReference?`); set after the first render of the default or substitute element, `null` while disabled, and `null` under a substitute callback (the part's JavaScript locates the host by id instead). Callback-handle cleanup semantics (RND-DOM-24) have no Blazor analogue |
| RND-DOM-34, RND-EDGE-04, RND-EDGE-05 (deferred elements) | vacuous: Blazor has no lazy element wrapper |
| RND-DOM-41 (handle receives the documented element class) | `ElementReference` is opaque; asserted in browser tests through `tagName` |
| RND-EVT-07 (non-DOM-argument handler chains) | change callbacks are typed `EventCallback` parameters, not bag entries; the part invokes them directly |
| RND-EVT-09 (chain returns the first handler's result) | handlers return `Task`; no return value |
| RND-ALG-13, RND-EVT-13 (handler identified by `on` + uppercase letter) | handler identified by `on` prefix plus delegate/`EventCallback` value, any casing |
| RND-DOM-27 (unprefixed id exceptions) | collapsed to the prefixed form |
| RND-EDGE-01/02/03 (dev warnings and the invalid-`render` error) | kept, with the message text adapted to Blazor terms; a `Render` fragment whose root is not an element or component frame throws RND-EDGE-03 |

## Consequences

* Parts are written in C#; `.razor` is for demos, docs and consumer code. A contributor template for `PartBase<TState>` is part of the implementation plan.
* The frame re-emitter is the one novel piece: it must handle every `RenderTreeFrameType` and is exercised by every part's conformance run on day one. Each render of a substituted part costs one scratch render of the consumer's fragment.
* Consumers get one small superset of Base UI (string plus function class/style at once) and one setup line (`AddBlazixPrimitives()`).
* Decision 4 owns what JavaScript receives about an event (`target`, `pointerType`, a native-event id) and the `preventDefault`/`stopPropagation` policy; this ADR fixes only the C# merge contract.

## Verification items

* Confirm that interactive activation replaces the prerendered subtree rather than reconciling attributes, and that multiple interactive roots activate in document order (affects how often RND-DOM-29's divergence case occurs). **Verified 2026-10-20 on both render modes (SDK 11.0.100-rc.2.26504.105):** `tests/browser/harness.spec.ts` "@verifies ADR-02/1 interactive activation replaces the prerendered subtree and roots activate in document order". The host tags every prerendered fixture node with an attribute Blazor never rendered before `blazor.web.js` starts; after activation no tagged node remains (replacement, not reconciliation), and two roots of the `prerender` fixture draw activation numbers 1 and 2 in document order from a per-circuit counter. [issue 3](https://github.com/JakeMurrayDev/Blazix.Primitives/issues/3).
* Confirm the frame re-emitter preserves `@key` and `@ref` semantics across re-renders for a substitute whose root is a consumer component (RND-DOM-43, RND-DOM-45). **Verified 2026-10-20 (M0 track 1, [issue 4](https://github.com/JakeMurrayDev/Blazix.Primitives/issues/4)): yes** — the re-emitter writes the consumer's `@key` with `SetKey` on the re-emitted component frame and re-emits its `@ref` as a component reference capture, so across re-renders of the part (its own `StateHasChanged` and new parameters) the consumer component keeps one instance, its capture action receives that instance, and a changed key disposes the instance and recaptures the new one. Permanent L2 tests: `SubstituteComponentIdentityTests` in `tests/Blazix.Primitives.Tests.Components/Rendering/`, tagged `[Trait("Verifies", "ADR02-2")]`.
* Measure the scratch-render cost on a list part (Menu items) before deciding whether the element form caches frames between renders.

## Considered options

* Substitution: callback only (old port), typed substitute object. Rejected: the first withdraws eleven of fourteen conformance IDs and the ergonomic core of composition; the second removes Razor markup from the substitute.
* Class/style: single `object` parameter mirroring the union (consumers would write `Class=`), or string and function mutually exclusive. Rejected for ergonomics.
* Veto: subclassed `EventArgs` copied per dispatch (no gain over the weak table); library-registered custom event types with a native-event id (deferred to ADR 04 as the event contract, not needed for the veto).
* Pipeline: child component per part (old port; double instance, ref race), static function with no base class (repetition).
* Ids: random per instance (guaranteed flip at activation), consumer-supplied required ids (breaks the no-props contract).

## Amendments

**2026-10-17, by ADR 05 (no-boxing constraint; .NET 11 / C# 15).**

* Decision 4's default state projection changes from cached reflection to a **source generator** emitting typed projection code per `[PartState]` record (reflection boxes every value on every render). Property order is declaration order by construction; RND-DOM-09 is then deterministic.
* Decision 1's two parameters (`Render`, `RenderFunction`) and Decision 2's `ClassValue`/`StyleValue` functions become **single union-typed parameters** where C# 15 unions are available: `Render : RenderFragment | RenderFragment<RenderProps<TState>>`, `ClassValue : string | Func<TState, string?>`, `StyleValue` likewise. The plain `class`/`style` strings still arrive through the unmatched bag and the P1 concatenation rule stands. The two-parameter shape remains the fallback if the Razor compiler does not bind attributes to union-typed parameters (ADR 05 verification item).
* The merged attribute bag is a typed entry list with a non-boxing `AttributeValue` union, emitted through `RenderTreeBuilder`'s typed `AddAttribute` overloads; `MergeProps` keeps a `Dictionary<string, object>` overload only for the public `useRender` surface.

**2026-10-18, by ADR 04 (dispatch-time decisions).** Decision 3's statement that `preventDefault` and `stopPropagation` are JavaScript policy is made concrete: Blazor's `@on…:preventDefault` / `@on…:stopPropagation` directives are rejected on parts and on substitute elements with a development-time error (new RND-EDGE diagnostic), and the consumer veto channels are `PreventBaseUIHandler()` from C# and `preventDefault()` from a consumer JavaScript listener. See ADR 04 Amendments 2026-10-18.

**2026-10-18, `inputRef` (combobox §16 item 5).** Following the RND-DOM-20..24 relaxation, `Combobox.Root.inputRef` (a handle to the hidden form input) has no port counterpart: `Combobox.Input.Element` is the visible input and the hidden input stays internal; the same applies to every other `inputRef`-style parameter (Checkbox, Radio, Switch, Slider thumbs).

**2026-10-18, by ADR 06 (React-assuming statements).** Withdrawn for the port, IDs kept: NUM-EDGE-07, POP-EDGE-08, CMB-STR-10, TAB-EVT-06; DLG-DOM-26 is rewritten without the hook name in the implementation revision.

**2026-10-18, verification.** Razor binds component attributes to parameters case-insensitively (`class="x"` → a parameter named `Class`; confirmed on SDK 10.0.301, see ADR 05 verification items). Decision 2's two channels therefore require that no part declares a parameter named `Class` or `Style` until the union-typed single parameter of ADR 05 §4 replaces them. Blazor event directives on a component tag compile to attribute frames (see ADR 04 Amendments 2026-10-18).

**2026-10-20, by ADR 08 (product-name rule).** The veto of Decision 3 is named `e.PreventPartHandler()` with the query `e.PartHandlerPrevented()` (previously `PreventBaseUIHandler()` / `BaseUIHandlerPrevented()`); semantics unchanged. The union-typed class and style parameters of the 2026-10-17 amendment are named `ClassValue` and `StyleValue` and the plain `class`/`style` strings keep arriving through the unmatched bag, so no part declares a parameter named `Class` or `Style` (ADR 08 §2). The generated id prefix stays `base-ui-`.

**2026-10-20, from the union-binding spike (issue 10; shape chosen by the user the same day).** The single union-typed parameters of the 2026-10-17 amendment are withdrawn for `Render` and for class and style. Decision 1's two parameters and Decision 2's function parameters stand as written, under ADR 08's names: `Render : RenderFragment` (the substitute element, with Razor's child-content form `<Render>…</Render>` available) and `RenderFunction : RenderFragment<RenderProps<TState>>` (the substitute callback, `<RenderFunction Context="props">…</RenderFunction>`), supplying both a development-time error; `ClassValue : Func<TState, string?>` and `StyleValue : Func<TState, string?>`, the plain strings arriving through the unmatched bag (P1 unchanged). Reason: Razor binds union-typed parameters (ADR 05 verification item, verified 2026-10-20) but offers no child-content element form for them (RZ10012) and converts no inline lambda or method group to a union without a cast to the case delegate type (CS1660, CS1503), so the union took template syntax and lambda inference away from the two parameters that use them most, while its one gain over the bag (`ClassValue="x"`) duplicated `class="x"`. Union types remain where ADR 05 §4 lists them for alternatives that are neither delegates nor fragments (`AnchorValue`, `AttributeValue`, `SliderValue`, the boolean-or-literal `[Union]` structs). The union types `RenderValue<TState>` and `ClassValue<TState>` are not created. No requirement ID changes; RND-API-01..11's parameter names were already ADR 08's.

**2026-10-20, always-on errors (M0 Track 1, issue 31; chosen by the user the same day).** Decision 1's "supplying both is a development-time error" and the directive-key diagnostic of ADR 04 Amendments 2026-10-18 (item 3) throw in every build, not only in development: both are misuse of a part by consumer code, the checks are deterministic and cheap, and a release build that hid them would render wrong silently. RND-EDGE-03 (a `Render` root that is neither an element nor a component frame) already throws in every build. The debug switch of ADR 05 §3 stays reserved for the development warnings (EVD-EDGE-01/02 and the Blazor form of RND-EDGE-01/02), never for these three errors.

**2026-10-20, RND-EDGE-01 and RND-EDGE-02 are vacuous for the port (M0 Track 1 review; chosen by the user the same day).** The relaxation row "RND-EDGE-01/02/03 (dev warnings and the invalid-`render` error): kept, with the message text adapted to Blazor terms" is narrowed to RND-EDGE-03. The warning of RND-EDGE-01 exists because a React component passed as the `render` function is called as a plain function; in Blazor a component type cannot be supplied where `Render` (a `RenderFragment`) or `RenderFunction` (a `RenderFragment<RenderProps<TState>>`) is expected, the mistake is a compile error, and a delegate has no name the pipeline could inspect. Both IDs are vacuous: no code, no test; their index rows keep the note `Port: vacuous (ADR 02 Amendments 2026-10-20)` when the document is next revised under conventions §3.5. RND-EDGE-03 stays as written (always-on, see the amendment above).

**2026-10-20, the `State` of `RenderElement<TState>` (issue 42 follow-up; chosen by the user the same day).** Decision 4's public `useRender` component keeps one generic form, `RenderElement<TState>`, whose `State` parameter is non-nullable and whose `RenderProps<TState>.State` is therefore never `null`. RND-API-07's default `state → {}` maps to `EmptyState`: when `State` is omitted and `TState` is `EmptyState`, the component uses `EmptyState.Instance`, which projects no attribute; when `State` is omitted for any other `TState` the component throws a `Blazix:` error at render. A non-generic `RenderElement` beside the generic one was rejected because Razor cannot disambiguate the tag `<RenderElement>` between the two (RZ10012, verified on SDK 11.0.100-rc.2). Base UI's test "handles undefined state" runs against `RenderElement<EmptyState>` without a `State`.

**2026-10-21, a part may decline a consumer handler by event name (M1 track 4, issue 61; option G2, chosen by the user the same day).** Decision 3's chain runs the substitute's handler, then the consumer's, then the part's. A part therefore cannot gate a consumer handler from its own handler. Base UI's button-like parts need that gate: they merge the consumer's props before the button mechanism, so its disabled gate covers the consumer's `onClick`, `onMouseDown`, `onPointerDown`, `onKeyDown` and `onKeyUp` (UBT-EVT-01/03, BTN-DOM-05).

`PartBase<TState>` gains `protected virtual bool ForwardsConsumerHandler(string eventName) => true`:
- The pipeline asks it once per consumer handler on every render, with the lowercase event name, and only for a value that is a handler (RND-ALG-13 as relaxed above).
- A declined handler is left off the element, so Blazor invokes nothing for it. A part that still needs the handler reads it from `AdditionalAttributes` and invokes it itself.
- A substitute element's own handlers are unaffected (RND §2.1 row 5). `RenderElement<TState>` declines nothing.
- The unmatched bag is not copied, so the hook allocates nothing.

`Button` declines the three pointer handlers while disabled, and declines the two key handlers always so that it can run them from its own handler. The rejected alternative (G1) was a per-part copy of the bag without the declined entries, written back to `AdditionalAttributes` on each parameter set. Tested by `tests/Blazix.Primitives.Tests.Components/Rendering/ConsumerHandlerForwardingTests.cs`.

**2026-10-21, the part's last word on its merged attributes (M1 track 6, issue 63; option H1′, recommended by the orchestrator and chosen by the user the same day).** The handover at attach (ADR 04 Amendments 2026-10-18) needs two things the pipeline did not give a part:
- its own declarations above the consumer's style (a collapsible panel's `animation-name: none` over the consumer's `animation-name`, COL-DOM-18);
- the style it rendered frozen from `attach` on, while the consumer's merged string travels to the module (COL-ANI-14, COL-DOM-17).

The Collapsible panel also does not merge the consumer's empty `id` (COL-API-10).

`PartBase<TState>` gains `protected virtual void FinishAttributes(AttributeList attributes)`:
- The pipeline calls it once per render, after `class`, `style` and the handlers are merged and before the default element, the substitute element or the substitute callback receives the attributes.
- What the part sets there wins over the consumer. A part may change there only an attribute its document names as part-owned or gives a documented fallback: the style it hands over to a module (the handover rows of ADR 04 Amendments 2026-10-18) and COL-API-10's empty `id`. Every other attribute keeps decision 2's rule that the consumer wins. The analyzers cannot see this, so it is a human check in `src/Blazix.Primitives/Rendering/CONTEXT.md`.
- The base changes nothing, and `RenderElement<TState>` answers through `IPartHost` with a no-op.
- Tested by `tests/Blazix.Primitives.Tests.Components/Rendering/FinishAttributesTests.cs`.

The rejected alternatives were:
- a narrower handover-only hook, which each handover part (the Collapsible panel, Avatar, every `Positioner` and `Arrow`, `Tabs.Indicator`) would need in its own variant;
- relaxing COL-DOM-18 and COL-ANI-14, which ADR 04's amendment of 2026-10-18 rules out.

(2) `PartBase<TState>` gains a protected virtual member the pipeline calls after the host element's closing frame, for the hidden inputs that Switch, Checkbox and Radio render as the root's next siblings (SWT-STR-01, CHK-STR-01, RAD-STR-01); the base renders nothing there. The Switch track (M2 track 4) writes it with its red L2 test, with sequence numbers inside the pipeline's region (BLZX2002), and with the dated note here that names the member, as `FinishAttributes` was written by the Collapsible track. **2026-10-22, the after-element member is `BuildAfterElement` (M2 track 4, [issue 80](https://github.com/JakeMurrayDev/Blazix.Primitives/issues/80); item 2 of the note above, chosen by the user 2026-10-22).** `PartBase<TState>` gains `protected virtual void BuildAfterElement(RenderTreeBuilder builder)`; the base renders nothing.
- The pipeline calls it once per render after the host element's frames on every path: the default element, a `Render` element or component root, and a `RenderFunction` callback. It wraps the call in a region at the new literal `AfterElementSequence = 102`, beside `ChildrenSequence` (100) and `TrailingCaptureSequence` (101), so the part numbers its own frames from 0 inside that region (BLZX2002, ADR 16 rule 3). The region is emitted, empty, for every part; it allocates nothing.
- It is not called while `Enabled` is false: the part renders nothing at all (RND-DOM-25), its siblings included.
- `RenderElement<TState>` renders nothing there. `src/Blazix.Primitives/Rendering/CONTEXT.md` has the human check (only the siblings the part's document places after the element), and `PartBase.template.md` points internal sibling elements to it.
- Tested by `tests/Blazix.Primitives.Tests.Components/Rendering/AfterElementTests.cs` and two titles in `RenderPipelineSequenceTests`.

**2026-10-26, a never-projected state field (M3 planning; chosen by the user 2026-10-26).** The projection generator gains a marker for a `[PartState]` field that belongs to the state (read by `ClassValue`, `StyleValue` and `RenderFunction`) and is never projected to an attribute, so that a non-primitive field compiles where BLZX1003 rejects it today. The first use is Accordion's value array in `AccordionRootState`, `AccordionItemState`, `AccordionHeaderState`, `AccordionTriggerState` and `AccordionPanelState` (ACC-STA-01, ACC-STA-02, ACC-STA-03, MUST), which makes Header, Trigger and Panel generic with their Item. Its own commit with its red generator test, by the Accordion track; the marker's name is the track's. The alternative, omitting the value from the records, was a port deviation on three MUST rows.

**2026-10-26, the marker is `[NotProjected]` (M3 track 6, [issue 105](https://github.com/JakeMurrayDev/Blazix.Primitives/issues/105); the note above, chosen by the user 2026-10-26; the name is the track's).** `Blazix.Primitives.Rendering.NotProjectedAttribute` is a property attribute beside `MirroredFieldAttribute`. `PartStateGenerator` skips a property that carries it, whatever the property's type, as it skips `[MirroredField]`, and BLZX1003's message names both markers. It is not `[MirroredField]`: the ownership lint requires a JavaScript-written registry entry for every mirrored field, and a never-projected field has no attribute at all. A generic `[PartState]` record keeps its type parameter list in the generated declaration and its hint name (`XState{TValue}.PartState.g.cs`). Tested by `tests/Blazix.Primitives.Tests.Generators/PartState/PartStateGeneratorTests.cs` (a marked list compiles while an unmarked one raises BLZX1003; a generic record projects its primitive fields).

**2026-10-27, typed callbacks of a component substitute (M3 track 4, [issue 103](https://github.com/JakeMurrayDev/Blazix.Primitives/issues/103); design point 14.8, settled by the orchestrator 2026-10-27 under decision 1).** The pipeline's component-substitute parameter binding keeps typed callbacks typed. Decision 1 gives a component root the part's merged attributes as parameters and keeps the component's own parameters as the objects Razor passed; an attribute of the substitute component whose name the component declares as a parameter is one of those, even when it is shaped like a handler (`OnPressedChange`, `OnCheckedChange`, an `EventCallback<T>`). The frame rewrite therefore merges into the handler chain only the `on*` attributes the component does not declare, the DOM handlers it captures as unmatched values. Before this note a declared typed callback was merged, re-emitted as an untyped `EventCallback` under its lowercase name, and failed Blazor's parameter binding with `InvalidCastException` (`<ToolbarButton Render="@<Toggle OnPressedChange="…" />">`). `Rendering/SubstituteParameters.cs` reads each component type's parameter names once. Tested by `SubstituteComponentParameterTests` (L2) and the Toolbar's Toggle and Switch titles in `tests/browser/toolbar.spec.ts`.

**2026-10-27, content before the host element: `BuildBeforeElement` (M4 planning, plan of 2026-10-27; chosen by the user the same day; written by M4 track 1 with its red L2 test, in its own commit).** `PartBase<TState>` gains `protected virtual void BuildBeforeElement(RenderTreeBuilder builder)`, the mirror of `BuildAfterElement` (Amendments 2026-10-22); the base renders nothing.
- The pipeline calls it once per render before the host element's frames on every path (the default element, a `Render` element or component root, a `RenderFunction` callback), inside a region at a new literal beside `AfterElementSequence = 102`, which track 1 names (BLZX2002, ADR 16 rule 3); the region is emitted, empty, for every part and allocates nothing. It is not called while `Enabled` is false (RND-DOM-25). `RenderElement<TState>` renders nothing there.
- Its first consumers are the focus guards a popup renders before an element: the portal's leading outside guard (the trailing guard and the `aria-owns` owner use `BuildAfterElement`; ADR 04 Amendments 2026-10-27) and a trigger's leading guard where a family's document places one. C# renders every guard; the module that owns the guard's behaviour listens on it.

- *The host wrapper (settled by the orchestrator 2026-10-27 on the track 1 brief's finding).* The hooks render beside the host element, so a part whose host must be the only child of a wrapper cannot get the wrapper from them: the Portal's host is the portal node (the consumer's attributes and `Render` go on it, FLT-DOM-11, PSH-STR-12) while ADR 04 Amendments 2026-10-27 wants the guards and the owner as the wrapper's siblings. `PartBase<TState>` therefore gains an opt-in host wrapper (track 1 names the member): when a part opts in, the pipeline emits one wrapper element around the host element's frames, at its own literals, with the part's wrapper attributes (`display: contents` for the Portal); `BuildBeforeElement` and `BuildAfterElement` render outside the wrapper; `Element` captures the host; a `Render` substitute or a `RenderFunction`'s output sits inside the wrapper; `FinishAttributes` concerns the host alone; no other part opts in and `RenderElement<TState>` never does. Written by track 1 with its red sequence tests in its own commit. The alternative, a `BuildRenderTree` override in the Portal, would repeat the pipeline's region and sequence rules in one part.

**2026-10-27, a handle's diagnostics (M4 track 1, [issue 117](https://github.com/JakeMurrayDev/Blazix.Primitives/issues/117); design point 6, settled by the orchestrator 2026-10-27 as the worker recommended, under Amendments 2026-10-20's always-on misuse errors and the plan's "Diagnostics" item the user accepted the same day; written in full by the implementing pull request).** A popup handle is created with `new` and holds no `ILogger`: it logs through the logger of the Root it last attached to, and a development warning raised before any Root ever attached is dropped (a dated note on PSH-EDGE-02, the one warning Base UI raises with no root). PSH-EDGE-01 and PSH-EDGE-03 throw in every build, as the document says; PSH-EDGE-02, 04 and 06 go through `DevelopmentWarnings.Write(ILogger, string)` behind the `Blazix.Primitives.DevelopmentWarnings` switch; PSH-EDGE-07 throws in every build under the always-on misuse rule, stricter than Base UI's "outside production" (a dated note).
