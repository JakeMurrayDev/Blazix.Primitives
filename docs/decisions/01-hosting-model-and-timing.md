| Status | accepted (2026-10-17) |

## Context

Base UI's behaviour is specified with seven timing terms (same commit; post-commit, pre-paint; after paint; next frame; microtask; macrotask; on animations finished; plus "committed synchronously"). Blazor has two interactive render modes with different timing, and `InteractiveAuto` runs the same component code in both:

* **WebAssembly.** Verified against `dotnet/aspnetcore` `main`: `WebAssemblyRenderer.UpdateDisplayAsync` hands the batch to `Blazor._internal.renderBatch` through a synchronous `[JSImport]` (JS applies it synchronously and never calls back into .NET during the batch) and returns a completed task; `Renderer.InvokeRenderCompletedCalls` then runs `OnAfterRender` synchronously. `Renderer.DispatchEventAsync` calls `ProcessPendingRender()` in its `finally`, so a synchronous event handler's render is in the DOM before the browser's event dispatch ends. `OnAfterRender` is therefore post-commit, pre-paint, and "committed synchronously" holds for synchronous handlers.
* **Server.** `RemoteRenderer.UpdateDisplayAsync` returns `pendingRender.CompletionSource.Task`, completed only when the client acknowledges the batch (`OnRenderCompletedAsync`); `OnAfterRender` awaits it. Every C# observation of the DOM is after paint plus a round trip; nothing in C# can affect the dispatching event. Synchronous JS-to-.NET invocation does not exist.

The earlier port (Blazix.BaseUI, 2025-12 to 2026-08) ran on both modes with browser-API-dependent code in JavaScript and C# mirroring state through asynchronous callbacks. The user judged its behaviour acceptable on both modes, including animations; its failure was elsewhere (no specification to build against, shared-utility structure, test strategy). That split is therefore kept.

## Decision

1. **Both interactive render modes are first-class targets. Server is the design floor.** No C# code may depend on pre-paint execution, same-task commit, or frame/microtask scheduling. Component code must not branch on render mode; the only mode-dependent capability is synchronous JS-to-.NET invoke, which may be used on WebAssembly solely for the conditional-prevent cases below and never to move state.
2. **Everything that needs a browser API lives in JavaScript. C# owns state, rendering and the consumer contract.** The boundary is drawn per *loop*, not per function (constraint C1): a loop that reads and writes browser APIs at frame rate (pointer drag, scroll-tracked positioning, animation watching, swipe arbitration) is JavaScript end to end, arithmetic included; everything else is C# calling JavaScript primitives that do one DOM thing each. Consequently every ALG-tagged requirement is implemented in exactly one language. Two implementations of one algorithm (the old port's duplicated `roundValueToStep`) are forbidden. Amended 2026-10-18: locale-dependent number formatting and parsing (`Intl.NumberFormat` in Meter, Progress and NumberField) is C# through .NET globalization, because the browser's `Intl` cannot be consulted synchronously during a Server render; the output is equivalent, not byte-identical (percent spacing, currency patterns), which is a port relaxation of MTR-I18N-01..03, PRG-I18N-01..03 and NumberField's formatting rows.
3. **C# never emulates frames or microtasks** (constraint C2): no `Task.Yield`, `Task.Delay(0)` or `SynchronizationContext.Post` standing in for `requestAnimationFrame` or `queueMicrotask`. Those terms are implemented in JavaScript or not at all. Amended 2026-10-18: a Base UI microtask whose purpose is "after every synchronous write of this commit" (PSH-STA-23's close-on-trigger-unmount check, FLD-FRM-17's re-commit) maps to the render-batch boundary, `OnAfterRender`, which is not emulation but the boundary doing the microtask's job; a microtask whose purpose is ordering against a browser event inside the same task stays JavaScript.
4. **Timing-term mapping** (normative for every document that uses the term):

| Canonical term | Implemented by | WebAssembly | Server |
|---|---|---|---|
| in the same commit | one render batch (attributes derived from one state object land together) | met | met |
| post-commit, pre-paint — DOM-only work (attribute/style writes, measurement) | the JS primitive that performed the write, or a JS `MutationObserver`/`ResizeObserver` callback on the applied batch | met | met |
| post-commit, pre-paint — C# state work (registry flush, value-changed side effects) | `OnAfterRender` | met | after paint plus one round trip |
| prop-to-store sync (UTL-STA-19..22) | `OnParametersSet` (ADR 05 §1; amended 2026-10-18) | met | met |
| after paint | `OnAfterRender` on Server; a JS `requestAnimationFrame` on WebAssembly when paint ordering matters | met | met |
| committed synchronously | `StateHasChanged` inside the synchronous part of the handler | met for synchronous handlers | not met (see table below) |
| next frame; microtask | JavaScript only | met | met in JS; C# learns the result a round trip later |
| macrotask / N ms | C# timers (`UTL-EVT-01..09` semantics) when the result is state; JS timers when the result is DOM | met | timer exact; DOM consequence lands a round trip later |
| on animations finished | JS watcher (`TRN-ALG-03`) notifying C# | met | notification, unmount render and its batch: about two round trips after the animation ends |

## Consequences

* The JavaScript layer is larger than a WebAssembly-only port would need, and it is the only place where frame-rate behaviour exists. ADR 04 enumerates its modules and the C#/JS contract.
* Tests of timing requirements must run in a real browser against both modes (ADR 06); bUnit cannot observe any row of the mapping.
* `docs/README.md` must link this table, and every component doc's §9 cites it where its IDs appear.
* Static server-side rendering (prerender) is out of scope for behaviour but in scope for markup: generated ids must be identical between the prerendered and the interactive pass (RND-DOM-29). That mechanism is ADR 02's.

## Verification items

* `WebAssemblyRenderer.UpdateDisplayAsync` defers its completed task by one `WebAssemblyCallQueue` turn when `HasUnstartedWork` is true; confirm during implementation that this never crosses a browser task boundary (if it did, `OnAfterRender` could run after paint in that case). **Verified 2026-10-20 (reading of aspnetcore `release/11.0`, `src/Components/WebAssembly/WebAssembly/src/Hosting/WebAssemblyCallQueue.cs` and `Rendering/WebAssemblyRenderer.cs`): the deferral never crosses a task boundary.** `WebAssemblyCallQueue.Schedule` is purely synchronous: when a call is in progress it enqueues the callback, and the outermost `Schedule` drains the queue in a `while` loop on the same stack before returning; there is no timer, promise or microtask anywhere in it. The `TaskCompletionSource` that `UpdateDisplayAsync` returns when `HasUnstartedWork` is therefore completed inside the outermost JS-to-.NET call (the event dispatch or `invokeMethod` that started the queue), and `Renderer.InvokeRenderCompletedCallsAfterUpdateDisplayTask` continues inline on the single-threaded runtime (no `SynchronizationContext` is installed, so the awaiter runs synchronously on `SetResult`). The DOM half holds independently: `RenderBatch` is a synchronous `[JSImport]`. Observed at run time by `tests/browser/harness.spec.ts` "@verifies ADR-04/2" (the render queued inside a synchronous `decide()` is in the DOM before the listener returns). [issue 1](https://github.com/JakeMurrayDev/Blazix.Primitives/issues/1).
* Measure the Server round-trip cost of the TRN-ANI-09 row on a realistic network before deciding whether ADR 04 adds the optimistic JS hide. **Measured 2026-10-21 (M1 track 6, Server):** `tests/browser/collapsible.spec.ts` "@verifies ADR-01/2 the closed panel is hidden at exit end ahead of its removal" (three titles, one per added round trip). Setup:
  * a non-kept `CollapsiblePanel` with a 100 ms height transition (`collapsible-css-transition`, `?animations=1`), closed 20 times per added round trip;
  * the delay is added by routing the circuit's WebSocket through the test with a delay each way (Playwright's own `page.routeWebSocket`). That is the "Playwright network throttling" of ADR 14 §1 for a Blazor Server circuit; Chromium's `Network.emulateNetworkConditions` (CDP) does not delay the WebSocket: a sync click measured about 1 ms with 100 ms emulated latency. The method change was accepted by the orchestrator on 2026-10-21;
  * a `MutationObserver` records `t0`, the module's convergent `hidden` at exit end, and `t1`, the render batch that removes the element.

  The gap `t1 − t0` is how long the closed panel would stay visible without the write:

  | Added round trip | Median | p95 | Max |
  |---|---|---|---|
  | 0 ms (localhost) | 1 ms | 2 ms | 10 ms |
  | 50 ms | 54 ms | 55 ms | 56 ms |
  | 150 ms | 156 ms | 158 ms | 159 ms |

  The removal lands about one round trip after the exit ends (the completion message to C#, then the batch back), not two as the TRN-ANI-03 row estimates. With the write, the closed panel is hidden in the task the exit ends, and that held in every run (`t0 ≤ t1`). 2026-10-21: measured median 1 / 54 / 156 ms at 0 / 50 / 150 ms added round trip without the hide, 0 ms with it; the optimistic hide stays (chosen by the user the same day). [issue 2](https://github.com/JakeMurrayDev/Blazix.Primitives/issues/2).

## Considered options

* **WebAssembly only.** Meets every timing term as written; rejected because it drops the common enterprise deployment and `InteractiveAuto`.
* **Both modes, Server best-effort.** Rejected because the Server half would be untested behaviour that `InteractiveAuto` users hit first.
* **Logic in C#, JS as thin primitives.** Rejected: on Server every per-event decision is a round trip late and the frame-rate loops lag visibly; `DRW-PTR-21` has no such form at all.

**2026-10-22, lifecycle order, the Enter macrotask and autofocus after prerender (M2 track 1, PR 1a, [issue 77](https://github.com/JakeMurrayDev/Blazix.Primitives/issues/77)).**
- **Lifecycle probe.** An L2 probe (`LifecycleOrderProbeTests`) records Blazor's order against FFI §8:
  - Blazor runs `OnAfterRender` parent before child. React runs layout effects child before parent.
  - A replaced component is disposed before the replacement's `OnAfterRender`: cleanup-before-setup holds.
  - The field parts rely on neither difference. A control claims its id and registers after its own render, and no enclosing part's after-render reads those registrations; each notifies the field scope. - **The Enter commit's task (settled by the orchestrator 2026-10-22 under ADR 01 decision 3's ordering clause).** Decision 3's amendment ("ordering against a browser event inside the same task stays JavaScript") is read to cover the 0 ms macrotask of FFI-ALG-16 too. - **Autofocus after prerender (settled by the orchestrator 2026-10-22, ADR 02 verification item 1 and ADR 15).** The interactive render replaces the prerendered DOM, so the focus the browser's `autofocus` gave a prerendered element is lost. **2026-10-23, consumer key handlers for a key the composite handles (M2 track 3, [issue 79](https://github.com/JakeMurrayDev/Blazix.Primitives/issues/79); option (i) of ADR 04 Amendments 2026-10-22, chosen by the user the same day).** The row "SLD-PTR-01 (default-prevented clause), EVD-EVT-26 against composite/button key handling, drag-start vetoes generally" gains its composite text.
- The `composite` module stops a key it handles at the root element (CMP-KEY-10, `stopEventPropagation`), before Blazor's document-level dispatcher, so no C# handler would run for it.
- WebAssembly runs the focused item's and the root's consumer `onkeydown` inside the decision point `navigate`, on one shared event, where either one's `PreventPartHandler()` stops the key: the requirement as written.
- On Server the module reports the key it handled (`CompositeTwin.KeyHandled`, sent only while such a handler exists). The two handlers then run a round trip later and cannot veto.
- An ancestor's handler never runs for the key, as in Base UI, where the root stops its propagation.
- Tested by `tests/browser/composite.spec.ts` (per mode) and `tests/Blazix.Primitives.Tests.Components/Composite/CompositeKeyHandlerTests.cs`. The alternatives were a new row under which those handlers do not run, and a deferred stop under which ancestors see handled keys.

**2026-10-27, a twin `update` sent from the commit path (M4 track 4, [issue 120](https://github.com/JakeMurrayDev/Blazix.Primitives/issues/120); design point 1, chosen by the user 2026-10-27; written in full by the implementing pull request).** The focus manager's inputs other than the open state (`Disabled`, which also gates the outside marking and the trap, FLT-FOC-19; the resolved initial-focus target; the open interaction type) are known at commit, and under the "JS-owned values that originate in C# state" row an `update` sent from `OnAfterRender` reaches the module a round trip after the batch on Server, so a modal popup would mark the page wrongly and leave its trap unarmed for that round trip.
