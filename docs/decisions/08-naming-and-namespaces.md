# ADR 08 — Naming and namespaces

| | |
|---|---|
| Status | accepted (2026-10-20) |
| Project | Blazix.Primitives |
| Decides | how Base UI part names become Blazor component type and tag names; the namespace layout; the names of state records, details, enums, unions, data-attribute constants, contexts, handles, twins and JavaScript modules; the parameter names for class and style; the rule for Base UI identifiers that carry the product name; member ordering and field naming |
| Affects | every part; RND-API-01..11 (parameter names), RND-EVT-03/04 (the veto's name), EVD §3.5 (the reason enum's name); amends ADR 02 decision 3 and ADR 05 §3 (names only) |

## Context

Razor resolves a component tag only when it is fully qualified or when its namespace is imported by a `@using` directive in a Razor file (verified on SDK 10.0.301 with a throwaway class library: `<Probe.Switch.Root>` compiled; `<Switch.Root>` under `@using Probe` and a nested-class `<Menu.Root>` both failed with RZ10012). C# global usings do not take part in tag resolution. Base UI reuses part names across families (Root in every family, Trigger in 20 documents, Popup in 15, Positioner in 11), so short class names per family collide as soon as two families appear in one file, which every form does. The old port used a namespace per family with flat names (`Blazix.BaseUI.Switch.SwitchRoot`); its demo pages carried up to eight `@using` lines each. The public surface will be around 900 types (the old port had 667). Fluent UI Blazor and MudBlazor put every component in one namespace. Base UI's single-part components are `Button`, `Input`, `Separator`, `Toggle`, `Form`, `DirectionProvider` and `CSPProvider`.

Razor binds component attributes to parameters case-insensitively (`class="x"` binds to a parameter named `Class`; verified 2026-10-18 and again 2026-10-20), so the name of the union-typed class parameter decides whether the plain `class` string reaches the unmatched bag. C# 15 unions are declared types, so the `string | Func<…>` shorthand of ADRs 02 and 05 needs named types. ADR 05 dropped Base UI's `BaseUI` prefix from the details types (`ChangeEventDetails`, `GenericEventDetails`, `HighlightEventDetails`) but kept it on `BaseUIEventReason` and on the veto `PreventBaseUIHandler()`; "Base UI" is MUI's product name and MIT grants no trademark rights. The old port's member order (eleven groups) was enforced by an analyzer that ended up suppressed because Roslyn did not apply the editorconfig to generated `razor.g.cs` files, a cause that disappears under ADR 02 (parts are plain C# classes). The old port forbade underscore prefixes on fields.

## Decision

### 1. Part names: flat, dot removed, one namespace (option N1)

A part `Family.Part` becomes the type and tag `FamilyPart`: `Switch.Root` → `SwitchRoot`, `Menu.CheckboxItemIndicator` → `MenuCheckboxItemIndicator`, `Popover.Positioner` → `PopoverPositioner`, `AlertDialog.Root` → `AlertDialogRoot`, `NavigationMenu.Viewport` → `NavigationMenuViewport`. Single-part components keep Base UI's name: `Button`, `Input`, `Separator`, `Toggle`, `Form`, `DirectionProvider`, `CspProvider`. Every part and its public companions live in the namespace `Blazix.Primitives`; a consumer adds one `@using`. Library-author surfaces live in sub-namespaces: `Blazix.Primitives.Rendering` (`PartBase<TState>`, `RenderElement<TState>`, `RenderProps<TState>`, `MergeProps`), `Blazix.Primitives.Store` (`Store<TState>`, `ComponentStore<TState>`, selectors), `Blazix.Primitives.Interop` (twins, internal). The mapping from a document's part name to the type name is mechanical (remove the dot) and tooling may rely on it.

### 2. Class and style parameters: `ClassValue` and `StyleValue` (two channels kept)

The union-typed parameters of ADR 05 §4 are named `ClassValue` and `StyleValue` (`string | Func<TState, string?>`). The plain `class` and `style` strings keep arriving through the unmatched bag and ADR 02's P1 concatenation rule stands (consumer string, then consumer function). No part declares a parameter named `Class` or `Style`. The one-line explanation for consumers: `class` is the Blazor attribute; `ClassValue` is Base UI's `className`, string or function.

### 3. Companion types

| Kind | Rule | Example |

A Base UI prop becomes a typed parameter; a pass-through HTML attribute (`id`, `aria-*`, `data-*`) stays in the unmatched bag | `nativeButton` → `NativeButton` |
| State record | `<Part>State`, a `sealed record` marked `[PartState]` | `SwitchRootState` |

### 4. Product-name rule

A Base UI identifier that carries the product name loses it in the port's C# surface: `BaseUIEventReason` → `EventReason`; `preventBaseUIHandler()` → `e.PreventPartHandler()`, with the query `e.PartHandlerPrevented()` ("part" is the glossary's word for the library's unit). The details types already follow this rule. DOM-level literals keep Base UI's form because tests pin them and consumers never type them: generated ids stay `base-ui-<n>` (RND-DOM-27, ADR 02 decision 5) and the harness switch stays `BASE_UI_ANIMATIONS_DISABLED` (TRN-EDGE-01). The documents keep Base UI's names throughout, as they do for `className`; the mapping is this ADR's.

### 5. Member order and field names

Members of every class follow the eleven-group order of the old port: constants, fields, private properties, parameter properties, public properties, internal properties, lifecycle methods, dispose, public methods, internal methods, private methods. Private fields carry no underscore prefix. Both are stated in the contributor template for `PartBase<TState>` (ADR 02) and enforced by the ordering and field-prefix analyzers of the analyzers project (ADR 09) once it exists, by review until then.

## Consequences

* ADR 02 decision 3 and ADR 05 §3 are amended for the names of the veto and the reason enum (see their Amendments sections); `CONTEXT.md` is updated.
* One wide namespace in IntelliSense; `Button`, `Input` and `Form` are generic names a consumer project may also define and disambiguate by namespace.
* A consumer who declares a parameter named `Class` on their own wrapper component captures the `class` attribute; the documentation says so once.

## Verification items

* Razor binds a literal to a hand-written `[Union]` struct parameter through its implicit conversion (`Modal="true"`, `Modal="@ModalValue.TrapFocus"`) on the .NET 11 SDK; if not, boolean-or-literal props fall back to two parameters (`Modal` and `ModalMode`). Tracked in ADR 14. **Verified 2026-10-20 (SDK 11.0.100-rc.2.26504.105): yes** — `Modal="true"`, `Modal="@isModal"` and `Modal="@ModalValue.TrapFocus"` bind to a hand-written `[Union] readonly struct ModalValue(bool, TrapFocusLiteral)` with an implicit conversion from `bool` (`System.Runtime.CompilerServices.UnionAttribute` and `IUnion` in `System.Private.CoreLib`; the compiler also synthesises the case conversions and treats a switch over the case types as exhaustive); the plain string `Modal="trap-focus"` does not bind (CS0103: a non-string parameter's value is C#). With `HasValue` and `TryGetValue(out T)` present, matching never reads `Value` and allocates nothing. The single-parameter shape stands; the `Modal`/`ModalMode` fallback is not needed. Finding recorded on [issue 10](https://github.com/JakeMurrayDev/Blazix.Primitives/issues/10).
* MUI's trademark position on "Base UI" appearing in an unofficial port's package description and acknowledgements (no API name carries it after this ADR). Tracked in ADR 14.

## Considered options

* Namespace per family with short class names (`Blazix.Primitives.Switch.Root`): tags fully qualified or one `@using` per family, and collisions between imported families; the Radix-style `<Switch.Root>` is unreachable in Razor. Namespace per family with flat names (the old port): the same usings for no gain. A library prefix (`BlazixSwitchRoot`): long tags that stop matching the documents.
* `Class`/`Style` as the union parameter names (one channel, exactly Base UI's shape): amends ADR 02's superset and depends on union binding; its fallback pair (`Class` string, `ClassValue` function) is worse than keeping `ClassValue`.
* A `Union` suffix on union types; an `Undefined` enum member (the old port's habit: a meaningless case in every switch that hides "not supplied" from the type).
* Keeping `BaseUIEventReason` and `PreventBaseUIHandler()` (another product's name in every veto call and reason switch, inconsistent with the unprefixed details types); renaming the id prefix and the harness flag too (every translated test asserting the prefix would change for a literal no consumer depends on).
* A light member order or none (drift across hundreds of agent-written classes); `_camelCase` fields (the wider .NET convention, rejected for continuity with the user's prior rule).

## Amendments

**2026-10-20, from the union-binding spike (issue 10; shape chosen by the user the same day; see ADR 02 and ADR 05 Amendments 2026-10-20).** §2 is amended: `ClassValue` and `StyleValue` are `Func<TState, string?>` parameters, not unions; the plain `class` and `style` strings keep arriving through the unmatched bag and the P1 concatenation rule stands; no part declares a parameter named `Class` or `Style`; the one-line explanation for consumers becomes "`class` is the Blazor attribute; `ClassValue` is Base UI's `className` as a function of state". §3's parameter row reads `render` → `Render` (substitute element) and `RenderFunction` (substitute callback). §3's union-types row loses `ClassValue<TState>` and `RenderValue<TState>`, which are never created; its examples are `AnchorValue`, `SliderValue`, `AttributeValue`, `ModalValue`. §5 gains a rule, analyzer-enforced with the other two: a union-typed `[Parameter]` is declared nullable. The "Considered options" entry on `Class`/`Style` as union parameter names is moot; the first verification item (hand-written `[Union]` struct binding) is unaffected and verified.

**2026-10-20, from M0 Track 0 (issue 30; chosen by the user the same day).** §5 is amended for static fields: a private static field, readonly or not, carries the prefix `s_` followed by camelCase (`s_instance`, the Microsoft runtime convention for statics). Private instance fields keep no prefix (`value`), constants stay PascalCase, and `_x` and `m_x` stay rejected for every field; the `_camelCase` bullet of Considered options still stands for instance fields. The rule is enforced in the build from Track 0 by IDE1006 through `.editorconfig`, ahead of the field-prefix analyzer of the analyzers project.

**2026-10-20, documentation comments on overriding and implementing members (user rule, given during M0).** §5 gains a rule: a member that overrides a base member or implements an interface member carries `/// <inheritdoc />` and nothing else as its documentation comment, so the contract is written once on the declaring member; a member that adds behaviour beyond the inherited contract uses `/// <inheritdoc />` plus a `<remarks>` block for the addition only. Enforced by review until the analyzers project gains a rule for it.

**2026-10-20, no specification references in the shipped surface (user rule, given during M0).** A documentation comment (`///`) on any member under `src/`, and any consumer-visible string (exception messages; analyzer and generator diagnostic titles, messages and descriptions), states the member's definition and behaviour in its own words and never references the specification: no decision-record number, no requirement ID, no section mark (`§`), no `docs/` path, no glossary pointer. Naming the Base UI concept a member ports (`Base UI's <c>mergeProps</c>`) is allowed; pointing the reader at a document is not. Traceability stays in ordinary `//` comments above the member and in the folder's `CONTEXT.md`, where IDs and record numbers are expected. Enforced by a lint over `src/` in CI (ADR 11 §5, added by Track 4 of M0) and by review until then; the 60 comment lines and 6 strings that existed when the rule was given are swept in M0.

**2026-10-20, documentation comments follow Microsoft's conventions (user rule, given during M0).** The shipped assemblies (`src/Blazix.Primitives`, `src/Blazix.Primitives.Generators`) set `GenerateDocumentationFile`, so under warnings-as-errors every public or protected type and member needs a documentation comment (CS1591) and every `cref`, `paramref` and `typeparamref` must resolve (CS1573, CS1574, CS1580, CS1584, CS1711, CS1712, CS1734). The comments use the tags and phrasing of Microsoft's "Recommended XML tags for C# documentation comments" and the .NET API documentation style: a `<summary>` of one or two complete sentences ending with a period; `<param>` for every parameter, `<typeparam>` for every type parameter, `<returns>` for every non-void method, `<value>` for every property, `<exception cref>` for every exception the member throws by design; property summaries start with "Gets" or "Gets or sets"; constructors read "Initializes a new instance of the <see cref="T"/> class" (or struct); `<see cref>` for types and members, `<paramref>` and `<typeparamref>` for parameters, `<see langword>` for `true`, `false`, `null`; `<c>` for inline code and `<code>` for blocks; `<remarks>` for anything beyond the contract; `<inheritdoc />` per the amendment above; no specification references per the amendment above. The analyzers project is internal and keeps the same style by review.

**2026-10-20, Blazor's conventional parameter names win (user rule, given during M0).** §3's parameter row is made explicit: where Blazor has a conventional name for a parameter's role, the part uses it. The child fragment is `ChildContent` (`RenderFragment?`); the unmatched attribute bag is `AdditionalAttributes` (`[Parameter(CaptureUnmatchedValues = true)] IReadOnlyDictionary<string, object>?`); a template parameter that takes a fragment with an argument is named for what it renders and is used with `Context`; the controlled pair is `<X>`, `<X>Changed` and `Default<X>` so that `@bind-<X>` works (ADR 05 §2). `RenderElement<TState>` keeps Base UI's `Props` for the explicit dictionary of attributes to merge, because it is not the unmatched bag. `PartBase<TState>` and `RenderElement<TState>` already comply; the rule binds every family from M1.

**2026-10-20, clarifications of the documentation-comment rules (from the independent review of PR 40, issue 42).** Boolean properties read "Gets a value indicating whether …"; spelling is US English; a `<typeparam>` reads "The type of …"; fields and constants are sentences starting "Represents …" (or "Specifies …" for options) and enum members are sentences too; the `<param>` of a positional record documents its synthesized property, which needs no `<value>` and no "Gets"; init-only properties read "Gets or sets …"; a single keyword is `<see langword>`, a multi-keyword fragment stays `<c>`; a member with `<inheritdoc />` may add `<exception>` as well as `<remarks>`; performance and implementation notes live in `<remarks>` or `//` comments, never in `<summary>`; every consumer-visible exception or diagnostic message starts with `Blazix: ` and quotes code in backticks. The CI lint of ADR 11 §5 (Track 4) checks the boolean wording and a US-spelling denylist.

**2026-10-20, enforcement in the build (M0 track 5, [issue 52](https://github.com/JakeMurrayDev/Blazix.Primitives/issues/52)).** §5's rules and the amendments above that add to them are build errors from the analyzers project (ADR 09), so "by review until then" and "until the analyzers project gains a rule for it" no longer apply. The member order is `BLZX2003`. The field names are IDE1006 through `.editorconfig` (Track 0) for private fields and constants, and `BLZX2004` for the fields IDE1006 does not reach: a probe on SDK 11.0.100-rc.2 found the naming rules cover every private field and every constant and no other field, so `BLZX2004` rejects `_x` and `m_x` on internal, protected, protected internal, private protected and public fields only. `<inheritdoc />` on overriding and implementing members is `BLZX2007`, with `<remarks>` and `<exception>` the only additions (the issue-42 clarification above). Nullable union parameters are `BLZX2006` (ADR 05 Amendments 2026-10-20). The analyzers run on the library and on the generator, the boxing rule of ADR 05 aside; local constants are not fields and neither IDE1006 nor `BLZX2004` checks them. Where §5 is silent, `BLZX2003` places as the track recommended and the user chose the same day ([pull request 56](https://github.com/JakeMurrayDev/Blazix.Primitives/pull/56)): constructors, the static constructor and the finalizer after the fields; events with the fields; protected and protected internal members with the public ones, private protected ones with the internal ones; explicit interface implementations and operators with the public members unless the name is a lifecycle or dispose name; `BuildRenderTree` with the lifecycle methods and `DisposeAsyncCore` with the dispose methods; nested types last. The groups, the placements and the IDE1006 probe are listed in `src/Blazix.Primitives.Analyzers/CONTEXT.md`.

**2026-10-21, `format` and `locale` on Meter and Progress (M1 planning; chosen by the user the same day).** §3's parameter row is made concrete for the two M1 families that format numbers: Base UI's `format` (`Intl.NumberFormatOptions`) is `Format : string?`, a .NET numeric format string applied through `double.ToString(format, culture)`; Base UI's `locale` is `Culture : CultureInfo?`, `null` meaning `CultureInfo.CurrentCulture` (Blazor's conventional name for a culture value; ADR 01 decision 2: .NET globalization, equivalent rather than byte-identical to `Intl`). With no `Format` the default is the percentage divided by 100 formatted with `"P0"` under the culture (MTR-API-04, PRG-API-04). A record mirroring `Intl`'s option names and a formatter delegate were considered and declined for M1; NumberField's `format` is decided when that family is briefed (M6), where ADR 01's rounding-mode helper applies.

**2026-10-21, the shared enum `Orientation` (M1 track 1, [issue 58](https://github.com/JakeMurrayDev/Blazix.Primitives/issues/58)).** §3's Enums row gets its first shared enum, named here as the companion-type table asks: `public enum Orientation { Horizontal, Vertical }` in `Blazix.Primitives`, declared in `src/Blazix.Primitives/Separator/Orientation.cs` beside its first consumer, `Separator`. **2026-10-22, parameter types for the M2 form family (M2 planning; chosen by the user the same day; the implementing pull request may refine a member on evidence, by a further dated note).**
- *Any-typed values.* A Base UI prop typed `any` or `unknown` and compared by identity (RadioGroup `value`, RAD-API-01; Select and Combobox in M5) becomes a type parameter: `RadioGroup<TValue>` and `RadioRoot<TValue>`, inferred by Razor from `Value` or `DefaultValue` and read by the items from the group's cascade; compared with `Equality.StrictEquals<TValue>`, which compares strings by ordinal value and floating point by value, and every other value type through `EqualityComparer<T>.Default`, which boxes integers and booleans as well as user value types on the WebAssembly interpreter (ADR 05 verification item 3, issue 11; corrected the same day, the first wording said the primitives do not box). - *Field and Form.* `FieldRoot.Validate : Func<FieldValidationArguments, ValueTask<FieldValidationResult?>>?`, with `FieldValidationArguments(object? Value, FormValues Values)` and `FieldValidationResult` convertible from `string` and `string[]` (`null` is valid); the `object?` slot boxes once per validation run, never per render, and the implementing pull request allow-lists it for `BLZX2005` with an ADR 05 note. `ValidationMode { OnSubmit, OnBlur, OnChange }` is a shared enum, since Field and Form share the literal set; `FieldRoot.ValidationMode` is `ValidationMode?`, `null` meaning the Form's. `ValidationDebounceTime : Duration?` (Amendments 2026-10-21). `Form.Errors : FormErrors?`, a dictionary type whose indexer accepts a `string` or a `string[]` and exposes `IReadOnlyList<string>` per key. `Form.OnFormSubmit : EventCallback<FormSubmitEventArgs>`, whose `Values : FormValues` is read-only with typed accessors over the one allow-listed `object?` collection; `Form.OnSubmit` runs only after validation passes. `actionsRef` on Form and Field.Root becomes public methods reached by `@ref` (`ValidateAsync()`, `ClearErrors(name)`), as `EditContext.Validate()` is reached. `FieldError.Match : MatchValue?`, a `[Union]` of `bool` and the enum `ValidityFlag` (the eleven `ValidityState` names). A control's `form` prop is `Form : string?`; inside that part the property hides the `Form` type, which the part does not reference. `Field.Validity` is a component without an element whose `ChildContent` is `RenderFragment<FieldValidityState>`.
- *`Input` and `FieldControl`.* Two sealed parts over one internal `FieldControlBehavior` (the `ButtonBehavior` pattern), each with its own state record, `DataAttributes` class and details names (INP §3.2); neither renders the other (ADR 16 rule 10) and neither derives from the other.
