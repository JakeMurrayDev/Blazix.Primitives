# Documentation conventions

These rules apply to every file under `docs/`. They exist so that forty-odd documents written by different authors read as one specification and can be traced back to the Base UI source line by line.

**In scope:** everything exported from `packages/react/src/index.ts` (41 modules) plus the internal mechanisms they rely on.
**Out of scope:** `filter-dropdown` and `internals/temporal*` (present in the tree but not exported in v1.9.0), the docs site itself, build tooling.

## 2. Audience and purpose

These documents are **requirements specifications** for re-implementing Base UI's behavior in a different language and UI framework (C#/Blazor, Rust, etc.). They are modeled on the WAI-ARIA Authoring Practices pattern pages: they describe *what* a conforming implementation does, observable from the outside (DOM output, attributes, timing, response to user input, callback contracts), not *how* React happens to do it.

The reader is a competent UI engineer who has **never read the Base UI source** and may not know React. Everything React-specific must be either translated into framework-neutral terms or quarantined in the "React-specific notes" section.

## 3. Requirement identifiers

Every normative statement carries a unique ID of the form:

```
<PFX>-<AREA>-<NN>
```

* `PFX` — the document prefix (table below). One prefix per document; a document never emits IDs under another prefix.
* `AREA` — a category code (table below).
* `NN` — two-digit sequence number within `PFX-AREA`, starting at `01`. Use three digits (`100`) only if a sequence exceeds 99.

Rules:

1. IDs are **never reused or renumbered**. If a requirement is deleted, keep the ID in the index with the statement "Withdrawn: <reason>".
2. New requirements are appended at the end of the sequence.
3. IDs need not appear in numeric order within the document (the template places some STA/DOM bullets in §3 and §5); the §15/§9 index restores the order.
4. Each ID covers exactly **one testable statement**. If a sentence contains "and", ask whether it is really two requirements.
5. Statements use RFC 2119 keywords in capitals: **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, **MAY**. Plain descriptive prose ("Base UI stores the value in…") is explanatory and is *not* a requirement; it carries no ID.
6. Use **MUST** for anything observable that the test suite or the public docs rely on. Use **SHOULD** for behavior that is implemented but is clearly a quality-of-implementation choice (e.g. a specific debounce duration). Use **MAY** only for explicitly optional behavior.

### 3.1 Requirement format

Write each requirement inline, where it is naturally discussed, in exactly this shape:

```
- **SWT-KEY-01** — MUST. Pressing <kbd>Space</kbd> while the Root has focus toggles `checked`.
  Source: `switch/root/SwitchRoot.tsx:112-118`. Test: `SwitchRoot.test.tsx` "toggles on Space".
```

* Source paths are relative to `reference/base-ui/packages/react/src/` unless they start with `packages/utils/`, `docs/`, or `test/` (the shared test harness and conformance suites in `reference/base-ui/packages/react/test/`, cited as `test/describeConformance.tsx:…`).
* Line numbers are from the pinned commit. A range is fine. Cite the line that *implements* the behavior, not the file header. Multiple files are separated by `;` or `, `; three to five citations are normal for a component that configures a shared mechanism.
* External specifications (ECMA-262, HTML, WAI-ARIA) are cited as `external: <spec> §<section>` after the repo call sites, never alone.
* Test citations give the file and the test title in quotes. Write `Test: none` when no test covers it; do not omit the field. For large test files a `Test:` line may cite a `describe` block with a count (`Test: MenuFilterRoot.test.tsx "text navigation" (10 tests)`) provided the §13 matrix maps every title. Canonical suite names: "conformance suite" (describeConformance), "popup conformance suite", "popup-list suite", "detached-triggers suite", "positioner conformance suite", "viewport conformance suite", "popup-focus-props suite", "dialog-root shared suite". Shared conformance suites may be cited by suite name and title (`Test: popup-list suite "closes on outside press"`), with the suite's options listed once in §13.
* When a requirement's body contains a table or code block, the single `Source: … Test: …` line follows the block.
* A requirement that is driven by a shared test suite but implemented in a mechanism owned by another document may cite that document's ID as its source: `Source: see FLT-FOC-03`.
* When a component's implementation is shared with another component (e.g. `Input` renders `Field.Control`), its `Test:` line may cite the other component's test file. A requirement exercised only by an architecture mechanism's tests may write `Test: see FFI-FRM-12` (the architecture ID whose `Test:` line covers it). Coverage-matrix placement follows the test file's directory.
* Errors a derived doc finds in its base doc go in its §16 "Base-doc discrepancies" sub-heading; errors any doc finds in an architecture doc go in a §16 "Related architecture-doc discrepancies" sub-heading. Both are repeated in the completion report; the orchestrator routes them to `docs/_qa-notes.md`.
* Adoption may be clause-level: `DLG-DIS-06 (nested-close clause) not adopted`, `CMB-STA-28 (sentence 1) overridden by AUT-STA-04`. Re-exported parts that are the base runtime component under a narrower public type are listed as "type-only alias" in the derived doc's §3 re-exported-parts table, with any runtime state fields the public type hides noted in §16.
* An adopting requirement in a derived doc may cite the base doc's §13 coverage matrix as its `Test:` evidence (`Test: see dialog.md §13`).
* A derived component doc (accordion over collapsible, alert-dialog/drawer over dialog, autocomplete over combobox, context-menu/menubar over menu) may adopt a whole range of base-doc IDs with one requirement plus a substitution table (`ACC-ANI-01: satisfies COL-ANI-01…30 with these substitutions: …`), and its §13 matrix may cite base IDs directly. Document individually only what the derived component adds or overrides.
* When an architecture doc already fully specifies a behavior, the component doc still issues its own ID phrased from the part's perspective (so the component's §15 index is complete on its own) and cites the architecture ID in `Source:`. Do not restate the mechanism's algorithm. The sanctioned form is a **configuration requirement**: "<Part> passes options O to mechanism M (Source: component line); the observable result is per <M-ID>." One such bullet may cover several mechanism IDs; do not split it artificially.
* The shared popup props (`handle`, `payload`, `actionsRef`, `id`, `triggerId`, `defaultTriggerId`, function-as-child, `createHandle`) are specified once in `architecture/popup-store-and-handles.md` §3; component docs cite those PSH IDs and list only component-specific defaults.
* Shared mechanisms whose warnings are emitted from component code (e.g. the `hiddenUntilFound`/`keepMounted` conflict warnings) are quoted in the architecture doc that owns the mechanism; the component doc cites that ID.
* If the behavior is documented in the official docs page, you may add `Docs: components/<name>/page.mdx §<heading>`. CHANGELOG entries are cited the same way: `Docs: CHANGELOG.md v1.7.0 "<entry title>"`.
* When a component *configures* a shared mechanism (e.g. passes options to `useButton`), cite both the component line that passes the option and the mechanism line that implements it, and link the architecture doc: `Source: \`switch/root/SwitchRoot.tsx:107\`, \`internals/use-button/useButton.ts:155-175\`; see [button-behavior](architecture/button-behavior.md).`
* Dev-only diagnostics (warnings/errors thrown only outside production) are **SHOULD** unless a test asserts them. Shared diagnostic messages are quoted verbatim once, in the architecture doc that owns the mechanism; component docs cite that ID and give only the substituted parameters. A component doc may raise a shared diagnostic to MUST when its own tests assert the message.

### 3.4 Implementation-revision marks (added 2026-10-20, per ADR 06)

Three marks were added to every document after approval so the documents drive the implementation and its tests directly. They are normative for the port only; the requirement statements still describe Base UI.

* **Test layer.** Every `Test:` line that cites a test carries one tag immediately after `Test: `, naming the lowest layer of ADR 06 §1 that can observe the requirement: `[L1]` xUnit (pure C# logic), `[L2]` bUnit (rendered C#-owned attributes and ARIA, controlled/uncontrolled contract, request sequences for C#-dispatched events, form integration, the conformance suite, twin contract tests), `[L3]` vitest (a JavaScript module in isolation), `[L4]` Playwright per render mode (anything crossing the C#/JS boundary: keyboard, focus, dismissal, positioning, animation, gestures, the shared popup suites, every row of ADR 01's relaxation table). Example: `Test: [L4] \`SwitchRoot.test.tsx\` "toggles on Space"`. `Test: none` and `Test: see <ID>` stay untagged. Where one bullet's citations need different layers, the tag is the lowest layer that observes the whole statement and the exception is noted after the citation (`(L4 for the animation clause)`). `docs/_tools/apply_layers.py` applies a per-document mapping (AREA defaults plus per-ID overrides) and lists what it could not tag.
* **Writer column.** Every §5 attribute, data-attribute and CSS-variable table in a component doc — or, where §5 tabulates nothing and the attributes are tabulated in §3, those §3 tables — gains a `Writer` column with one of `C#` (rendered by the part), `JS` (written by a JavaScript module; C# mirrors the value into the state object and excludes it from projection), or `C# → JS` (rendered once by C#, owned by JavaScript from attach; ADR 04 Amendments, handover at attach). Values follow ADR 04 §2's ownership list as amended; everything not listed is `C#`.
* **Server relaxations.** §9 of every component doc (and §4 of an architecture doc, before the first ANI or STA requirement it affects) ends with a sub-list *Server relaxations* naming each of the document's IDs that appears in ADR 01's relaxation table with the substitute column's text, citing `decisions/01-hosting-model-and-timing.md`. The bullet of each such ID gains the trailing sentence `Server: relaxed, see §9` (component) or `see ADR 01` (architecture).
* **React-assuming statements** are rewritten under the three rules of ADR 06's amendment of 2026-10-18; a withdrawn-for-the-port ID keeps its bullet and index row with the note `Port: withdrawn (ADR 02 Amendments)`.

### 3.5 Amendments after approval (added 2026-10-20, per ADR 13)

After a document is `approved`, a change to a requirement bullet (statement, level, `Source:`, `Test:` tag, `Writer` cell) keeps its ID (append or withdraw, never renumber), carries a dated note in the bullet or in §16 (component) / §10 (architecture), and cites the decision record or amendment that caused it when it is a port decision; a fidelity correction against the pinned source needs the dated note and a line in `_qa-notes.md`, no decision record. The front-matter table gains a `Revised` row holding the latest amendment date. A layer-tag or `Writer` correction found while implementing is made in the implementing change under the same rule. Only the user sets `approved` and `implemented`. There is no separate changelog.

## 4. Writing rules

* **Observable behavior only.** Describe DOM, attributes, timing, and input/output. "The hook re-runs" is not observable; "the attribute updates within the same frame" is.
* **Translate React vocabulary** on first use, then use the neutral term:
  * *prop* → keep "prop" (it is understood), but define a part's props as "its public parameters".
  * *`render` prop* → "element substitution": the consumer supplies the element/component to render in place of the default, and the part merges its own attributes and handlers onto it.
  * *ref* → "DOM handle".
  * *context* → "ancestor-provided shared state"; name which ancestor part provides it.
  * *controlled / uncontrolled* → value owned by the consumer vs. owned by the component; always name the prop pair (`value`/`defaultValue`, `open`/`defaultOpen`, …).
  * *state attributes* → `data-*` attributes derived from the part's state object.
  * *event details* → the structured second argument passed to change callbacks (`reason`, `event`, `trigger`, `cancel()`, `allowPropagation()`, `isCanceled`, `isPropagationAllowed`).
* **Keyboard tables** list every key the source handles, with modifiers, and what happens when the key is *not* handled (e.g. "Tab is not intercepted; native focus movement occurs").
* **Enumerate exhaustively.** Every prop, every `State` field, every data attribute, every CSS variable, every `reason` string, every thrown/warned message, every ARIA attribute. Cross-check against `components/page.mdx` and the `*DataAttributes.ts` / `*CssVars.ts` files; if the source has something the outline lacks (or vice versa), document it and note the discrepancy.
* **Tests are the behavioral spec.** Read every `*.test.tsx` for the component. Anything a test asserts that the prose does not already capture gets its own requirement ID (component docs: §13; architecture docs: the relevant §4 area).
* **Timing is a requirement.** Delays, debounce intervals, animation-frame deferrals, and "next tick" behaviors must be stated with their values and the condition that triggers them. Use this canonical vocabulary, identically in every document:
  * **post-commit, pre-paint** — synchronously after the DOM has been updated for a state change and before the browser paints (React layout-effect timing).
  * **after paint** — after the browser has painted the updated DOM (React passive-effect timing); no specific frame guaranteed.
  * **next frame** — one animation frame after the triggering event (`requestAnimationFrame`); **two frames** = nested rAF.
  * **microtask** — before the next macrotask, after the current synchronous work.
  * **macrotask / N ms** — a timer with the stated delay (`0 ms` for "next macrotask").
  * **on animations finished** — when all finite CSS animations/transitions on the element (and, if stated, its subtree) have ended or been cancelled, per the transitions-and-mounting doc.
  * **committed synchronously** — the DOM update is forced to complete inside the event handler that caused it, before the handler returns (React `flushSync`).
* **Defaults are requirements.** Every default value is stated in the props table and, where non-trivial (computed, environment-dependent), has a requirement.
* **Do not speculate.** If the source is ambiguous, say so in the Open questions section (§16 in component docs, §10 in architecture docs) with the file:line that is unclear. Do not invent behavior to fill a template section; write "Not applicable" with one sentence of justification.
* **Internal helpers.** When a component delegates to a shared mechanism (e.g. `useButton`, `useAnchorPositioning`, `CompositeRoot`), do not re-document the mechanism. Link to the architecture doc and state *only* the component-specific configuration (which options it passes, what it overrides). If the architecture doc does not exist yet, link to its planned filename from §3.2 anyway.
* **Shared suites.** For every shared suite a component runs (`describeConformance`, popup, popup-list, detached-triggers, positioner, viewport, popup-focus-props, dialog-root), the §13 row lists the options the component passes and the architecture IDs the suite exercises; the component issues its own IDs only for component-specific outcomes.
* **Conformance obligations.** The rules every part must satisfy (ref forwarding, `render`/`className`/`style` function support, prop forwarding, data-attribute emission) are specified once in `architecture/rendering-and-composition.md` §4.9 (RND-DOM-36 … RND-DOM-49). Component docs cite those IDs in their §13 matrix row for the `describeConformance` suite and record only the options the component passes to it.
* **No implementation.** These docs contain no C#, Rust or other target-language code. Pseudo-code is allowed in architecture docs (§ALG) when an algorithm must be reproduced exactly; keep it language-neutral.
* **No marketing prose.** No "high-quality", "powerful", "seamless".

## 5. File layout

```
docs/
  README.md                  index, status table, reading order
  conventions.md             this file
  _templates/
    component-template.md    copy verbatim for every component doc
    architecture-template.md copy verbatim for every architecture doc
    analysis-brief.md        instructions given to each analysis author
  architecture/<kebab>.md    one per PFX in §3.2 architecture table
  components/<kebab>.md      one per component (grouped docs use the primary component's name)
```

Document file names match the Base UI source directory name (`number-field.md`, not `NumberField.md`).

## 6. Status values

Front-matter table `Status` field: `draft` (author finished, unreviewed) → `reviewed` (second-pass QA done, discrepancies resolved) → `approved` (user sign-off; implementation may begin) → `implemented` (the component meets the done definition of `decisions/13-document-status-and-amendments.md` §1: every §13 row green at its layer, L4 on both render modes; set by the user).
