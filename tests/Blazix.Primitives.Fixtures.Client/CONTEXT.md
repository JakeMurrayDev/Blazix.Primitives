# tests/Blazix.Primitives.Fixtures.Client

The fixture components and the harness services, in a Blazor WebAssembly project so the host can render them in both interactive modes.

## Inputs

- `../../src/Blazix.Primitives` (internals visible: the probe twin derives from `TwinBase`), `Microsoft.AspNetCore.Components.WebAssembly` and `Microsoft.Extensions.TimeProvider.Testing` on the pinned versions.
- `docs/components/<family>.md` §13: the scenarios the browser tests need a page for.
- Decision record 06 §2: readiness markers, prerendering off by default, clocks, diagnostics.

## Job

- `FixtureCatalog`: name → `FixtureEntry(Component, Prerender, Roots)`; the host resolves `/{mode}/{fixture}` through it.
- `FixtureContainer.razor`: the wrapper every fixture renders: `data-fixture`, `data-interactive`, `data-renderer`, `data-session`; binds the circuit's dispatcher to the session for diagnostics attribution and registers the session's object reference with `window.blazixFixture` on the first interactive render.
- `Harness/`: `FixtureSession` (scoped: token, `FakeTimeProvider`, captured diagnostics, `[JSInvokable] AdvanceTime` and `DiagnosticsJson`), `FixtureSessionRegistry` (singleton: by token for the endpoints, by renderer `SynchronizationContext` for the logger), `CapturingLoggerProvider`, `ActivationCounter`, `AddFixtureHarness`.
- `Probe/`: the harness canary: `ProbeTwin`, `ProbeOptions`/`ProbeClick`, `ProbeFixture.razor`; `js/probe.ts` is its module, built by the library's esbuild script into `wwwroot/js/` (ignored by git) and served at `/js/probe.js` (the client project is served at the site root).
- `ButtonBehavior/`: the `button-behavior` fixture: plain elements with a `ButtonTwin` each (non-native, vetoed by C#, composite, link, native composite, submit, reset, two twins on one element), click counts from Blazor's own `onclick`, `data-attached` once every twin is attached, and a sync button the specs click as a barrier before asserting counts. The attributes a part would render are written by hand; it tests the module, not a part.
- `Button/`: the Button family's fixtures (`button-native`, `button-focusable`, `button-custom`, `button-link`, `button-loading`; `tests/browser/button.spec.ts`), in the namespace `ButtonFixtures` so no `Button` namespace hides the `Button` type. `ButtonFixtureBase` renders `data-attached` once every Button's internal `TwinAttached` task has completed and counts the sync button; `ButtonCaseFrame` renders one case's consumer-handler counts as data attributes between a native button before and one after it.
- `Avatar/`: the Avatar family's fixtures (`avatar-preload`, `avatar-kept-mounted`, `avatar-delay`, `avatar-render-function`, and the prerendered `avatar-prerender-preload` and `avatar-prerender-kept-mounted`; `tests/browser/avatar.spec.ts`), in the namespace `AvatarFixtures`. Each renders the image's reported statuses as `data-statuses`; the image is `wwwroot/avatar.png`, served at `/avatar.png` with a query the specs match to hold or answer the request.
- `Collapsible/`: the Collapsible family's fixtures (`collapsible-basic`, `-css-transition`, `-css-animation`, `-render-function`, `-initially-open` (prerendered), `-reattach`, `-hidden-until-found`; `tests/browser/collapsible.spec.ts`), namespace `CollapsibleFixtures`. Each case is a `CollapsibleCaseFrame` that renders its `OnOpenChange` record as data attributes; `CollapsibleFixtureBase` renders `data-attached` once every listed root, trigger and initially rendered panel is attached and counts the sync button. The `-reattach` fixture stands in for React.Activity with the panel's `Enabled`. The project turns the library's development warnings on (`RuntimeHostConfigurationOption`, as the host does), so the specs read them from the diagnostics.
- `Accordion/`: the Accordion family's fixtures (`accordion-basic`, `-css-transition` (open with `?animations=1`), `-initially-open` (prerendered), `-reattach`, `-hidden-until-found`; `tests/browser/accordion.spec.ts`), namespace `AccordionFixtures`. Each case is an `AccordionCaseFrame` that renders its `AccordionCase` record (the item `OnOpenChange` and root `OnValueChange` calls, the last of each with its reason and event; cancel switches; a controlled value) as data attributes; `AccordionFixtureBase` renders `data-attached` once every listed trigger, initially rendered panel and `AccordionRevealCase` is attached and counts the sync button. The `-reattach` fixture stands in for React.Activity with the panel's `Enabled`, as Collapsible's does.
- `Composite/`: the `composite` module's fixtures (`composite-list`, `composite-rtl`, `composite-reorder`, `composite-selection`; `tests/browser/composite.spec.ts`), namespace `CompositeFixtures`. Base UI's composite root is internal and no public root exists before RadioGroup, so `FixtureCompositeRoot` and `FixtureCompositeItem` are test-only parts composing `CompositeRootBehavior` and `CompositeItemBehavior` (public, because Razor finds only public components). `CompositeFixtureBase` renders `data-attached` once every root's twin is attached and counts the sync button. `CompositeKeyProbe` counts the consumer's C# `onkeydown` runs on a root, its items and an ancestor, with a switch that makes the root's handler call `PreventPartHandler()`. `composite-selection` puts a hand-written `<input type="radio">` after each item, as Radio renders its hidden input, and renders the reports as data attributes.
- `Composite/`: the `composite` module's fixtures (`composite-list`, `composite-rtl`, `composite-reorder`, `composite-selection`; `tests/browser/composite.spec.ts`), namespace `CompositeFixtures`. Base UI's composite root is internal and no public root exists before RadioGroup, so `FixtureCompositeRoot` and `FixtureCompositeItem` are test-only parts composing `CompositeRootBehavior` and `CompositeItemBehavior` (public, because Razor finds only public components). `CompositeFixtureBase` renders `data-attached` once every root's twin is attached and counts the sync button. `CompositeKeyProbe` counts the consumer's C# `onkeydown` runs on a root, its items and an ancestor, with a switch that makes the root's handler call `PreventPartHandler()`. `composite-selection` puts a hand-written `<input type="radio">` after each item, as Radio renders its hidden input, and renders the reports as data attributes. M3 track 1 (issue 100) adds four fixtures and two hosts:
  - `FixtureCompositeRoot` gains `HighlightItemOnHover`, `DisabledIndices`, `DeriveDisabledIndices`, `ReportItems` and `FollowActiveItem`; `FixtureCompositeItem` gains `Disabled` and `FocusableWhenDisabled`.
  - `FixtureCompositeList` and `FixtureCompositeListItem` compose `CompositeListBehavior` and `CompositeListItemBehavior`; the item renders its index as `data-index`, and `CompositeFixtureBase` waits for the lists too.
  - `composite-nested`: Base UI's `NestedItemsRoot`, outer items focusable when disabled whose element is an inner item that is not.
  - `composite-flags`: a button outside the root toggles an item's `Disabled` and its `data-disabled` in one batch.
  - `composite-follow`: the fixture renders the active marker on the selected item; a button outside the root selects the next item, and Enter on an item selects the item after it from C#.
  - `composite-registration`: keyed sections each holding a list item, with buttons that add an item at the front and reorder the sections.
- `FocusManager/`: the `focus-manager` module's fixtures (`focus-manager-modal`, `focus-manager-kept-mounted`, `focus-manager-empty`, `focus-manager-restore`, `focus-manager-non-modal`, `focus-manager-composite`, `focus-manager-portal`; `tests/browser/focus-manager.spec.ts`), namespace `FocusManagerFixtures` (2026-10-27, M4 track 4, issue 120; revised 2026-10-28, when the popup core was on `main`). No public part manages focus before Popover and Dialog, so `FixtureFocusManaged` is a test-only Popup part (`PartBase<EmptyState>`) composing `FocusManagerBehavior` (`../../src/Blazix.Primitives/Floating/`) as a family's Popup will: the inputs from `OnParametersSet`, so changed options are sent before the batch that applies them (design point 1 (d), chosen by the user 2026-10-27; `?push=after` on `focus-manager-kept-mounted` sets them from `OnAfterRender` only), both inside guards and the publication to an enclosing portal from the behavior, the Popup parts' focusable props, `data-open` while open and `data-handle-attached` once attached. Its parameters are the behavior's inputs but the element targets (ids only) and the relay; the close type is classified by the behavior from `CloseEvent`. `FocusManagerFixtureBase` plays the popup store (a trigger toggles, Escape and a focus-out request close, handing the close's `EventSnapshot` to the popup) and renders `data-attached` and `data-focus-out-closes`; the non-modal page's cancel switch refuses the close as a consumer's cancel would. `focus-manager-portal` is FloatingFocusManager.test.tsx's "non-modal + FloatingPortal" App inside track 1's `FixturePortal` (`?composite=true` puts a composite group in the popup).
- `Field/`, `Fieldset/`, `Input/`: the Field, Fieldset and Input fixtures (namespaces `FieldFixtures`, `FieldsetFixtures`, `InputFixtures`; `tests/browser/field.spec.ts`, `fieldset.spec.ts`, `input.spec.ts`).
  - The pages: `field-basic`, `field-validation`, `field-label-non-native`, `field-autofocus` (prerendered; `?control=input` renders an Input), `field-edit-form` (Blazor's `EditForm` with `DataAnnotationsValidator`, for `@verifies ADR-05/5`), `fieldset-basic`, `fieldset-prerender` (prerendered) and `input-showcase`; in PR 1c `field-error` (Field.Error's message, id and transition; open with `?animations=1`), `field-custom-validity` (the custom validity ownership titles that render Field.Error or Form) and `field-form` (the FieldRoot and FieldControl titles with Form or Field.Validity, validator calls rendered as data attributes).
  - `FieldFixtureBase` renders `data-attached` once every listed control and label has the form module attached and every listed field error has the transitions module attached, and counts the sync button. `field-basic`'s `remount` case counts its control's attaches, so the spec types only into an attached control. A validator renders its page after it records a call, since the field's own work renders only the field's parts.
- `Form/`: the Form fixtures (namespace `FormFixtures`; `tests/browser/form.spec.ts`): `form-submit` (OnSubmit with the re-issue, the veto, OnFormSubmit's values), `form-blocked` (custom and native errors; keyed fields reversed), `form-native-validation` (`NoValidate="false"`), `form-external-errors` (an `Errors` swap after a passed submission), and in PR 1c `form-errors` (the Form.test.tsx titles that render Field.Error) and `form-registration` (the registry titles of FFI-FRM-17 in the browser). They derive `FieldFixtureBase`, which also waits for a `Form`'s attach.
- `Radio/`, `RadioGroup/`: the Radio and RadioGroup fixtures (namespaces `RadioFixtures`, `RadioGroupFixtures`; `tests/browser/radio.spec.ts`, `radio-group.spec.ts`): `radio-standalone`, `radio-native-button`, `radio-indicator` (open with `?animations=1` for the transition cases) and `radio-group-basic`, `-controlled`, `-rtl`, `-field`, `-fieldset`, `-form`, `-edit-form` (for `@verifies ADR-05/5`) and `-allocation` (the WebAssembly half of the value-comparison probe). Each case is a `RadioCaseFrame` that renders its `RadioCase` record (OnValueChange with its event, the consumer's clicks and key presses, their order) as data attributes between a native button before and one after it; `RadioFixtureBase` renders `data-attached` once every tracked radio, group and indicator is attached and counts the sync button. A `Form`'s `OnFormSubmit` values render as the case's `data-values`.
- `Toggle/`, `ToggleGroup/`: the Toggle and ToggleGroup fixtures (namespaces `ToggleFixtures`, `ToggleGroupFixtures`; `tests/browser/toggle.spec.ts`, `toggle-group.spec.ts`): `toggle-standalone`, `toggle-composite-root` (a bare Toggle between two items of `FixtureCompositeRoot`, TGL-EDGE-09), `toggle-group-orientation` (a group per direction and orientation under a `DirectionProvider`, with the opposite `dir` attribute) and `toggle-group-basic`. Each case is a `ToggleCaseFrame` that renders its `ToggleCase` record (the toggles' `OnPressedChange`, the group's `OnValueChange`, the consumer's clicks, pointerdowns and key presses, their order, and the switches that make a consumer handler call `PreventPartHandler()`) as data attributes between a native button before and one after it; `ToggleFixtureBase` renders `data-attached` once every tracked toggle, group and test root is attached and counts the sync button.
- `Popup/`, `Portal/`, `ScrollLock/` (M4 track 1, issue 117; namespaces `PopupFixtures`, `PortalFixtures`, `ScrollLockFixtures`): Base UI's popup store, `FloatingPortal` and `useScrollLock` are internal, so the shared popup layer is proven on public test-only hosts (Razor binds only public components; settled by the orchestrator 2026-10-27, plan §Settled "Test-only hosts"). The project runs the generators on their state records (`[PartState]`, `[StoreState]`).
  - `FixturePopupRoot`, `FixturePopupTrigger` (a C# `onclick` toggle, design point 4), `FixturePopupPortal` (rendered while mounted, a boundary part), `FixturePopupPopup` (the `transitions` handle after the portal's move, `hidden` when kept and not mounted) and `FixturePopupClose`, generic over `TPayload` (`NoPayload` for a plain popup), with `FixturePopupHandle<TPayload>`.
  - `PopupSuiteFixtureBase`: the shared suites' fixture contract (`?case=` and the root's props from the query, the callbacks as `data-open-changes` and `data-open-change-completes`, `data-attached`, the sync barrier), inherited by the popup families' suite fixtures (tests/browser/CONTEXT.md, `suites/`).
  - The pages: `popup-conformance`, `popup-triggers` (contained or detached triggers with payloads, nesting, root mount and handle buttons, the programmatic and overlap cases, `throws=false`), `popup-unmount` (PSH-STA-23), `portal-basic` (`FixturePortal`, issue 8's siblings and children, the containers) and `scroll-lock-basic` (`FixtureScrollLock`, two locks on a tall page).
  - `FixturePortal` and `FixturePortalFocusPublisher` (a stand-in for the focus manager's publication) also serve `checkbox-group-portal` and `radio-group-portal`, the seven portal titles left open to M4 by the M2 groups.
- `Prerender/`, `Allocation/`, `KeepAlive/`: the fixtures of the M0 verification items (ADR-02/1, ADR-06/1, ADR-05/3, ADR-06/2).

## Outputs

- The client assembly and its WebAssembly bundle, served by `../Blazix.Primitives.Fixtures`.
- The pages `tests/browser/*.spec.ts` navigate to.

## Human check

- A fixture needs no code the user of the library would not write, except the harness canary.
- It renders identically in both render modes except where ADR 01's relaxation table says otherwise.
- A page exists for each `Test:` row tagged `[L4]` that needs one, for each verification item, and for no other reason.
