# src/Blazix.Primitives/Composite

The C# half of the composite mechanism: the root and item behaviours a roving group's parts compose (ADR 09 Amendments 2026-10-22: a mechanism's C# half lives in a folder named after the mechanism when no family owns it). The JavaScript half is `../js/composite.ts` and the twin is `../Interop/CompositeTwin.cs`. Namespace `Blazix.Primitives`, every type internal (Base UI's `CompositeRoot`, `CompositeItem` and `CompositeList` are internal, CMP §3; ADR 08 §1 gives them no part names).

## Job

| File | Role |
|---|---|
| `CompositeRootBehavior.cs` | One root's mechanism, composed into the root part as `ButtonBehavior` is (never a nested component, ADR 16 rule 10). It owns one `CompositeTwin` and its handle, and attaches it as `ButtonBehavior` does: by `Element`, by the generated id under a substitute callback, or by a late id. The part sets the options on every parameter set: `Orientation` (a literal from `CompositeLiterals`), `LoopFocus`, `EnableHomeAndEndKeys`, `StopEventPropagation`, `HighlightItemOnHover`, `ModifierKeys`, `DisabledIndices`, `SelectOnNavigation`, `ReportFocusLeave`, `ReportHighlight`. It reads the nearest `DirectionProviderContext` (`ltr` without one) and re-renders the part when the direction changes. It sends one `update` per render batch that changed the options, the item ids, an item's consumer `tabindex` or an item's element, and nothing for an unchanged render. It mirrors the reports: `HighlightedIndex` (0 until a report) with `HighlightChanged` raised once per change, and `FocusLeft`. It gates the consumer's `onkeydown`: the part declines it and runs it from its own handler, or the `navigate` decision runs it on WebAssembly, with the one-shot marker. Option (i) of ADR 04's note of 2026-10-22, chosen by the user 2026-10-23: `navigate` runs the focused item's handler first, on the same event, and on Server the module's handled-key report runs both; `ReportHandledKeys` is sent only while a handler exists. The part's own chains are `NavigationDecider` and `SelectionDecider`. |
| `CompositeRootBehavior.cs`, M3 (track 1) | Three more options the part sets on every parameter set, each sent only when set and compared before the options are built. `DeriveDisabledIndices` (E3, ToolbarRoot): the module derives the skipped indices from the items' flags. `ReportItems` (E2, TabsList; ToolbarRoot if it needs it): the module reports the items' ids in index order, and the behaviour joins them to its registrations as `OrderedItems` (the first per id; unknown ids ignored; a removed item dropped), raising `ItemsChanged` once per report, before or after the handle exists. `FollowActiveItem` (E5, TabsList): the highlight follows the item marked `data-composite-item-active` unless it is `aria-disabled="true"`. E4: when two items register one id (an outer item whose element is an inner item, a `Toolbar.Button` substituting a `Toggle`), the root sends the first registration per id, the outer item's, since parameters are set parent before child. The items version moves only for a registration that is or was the first for its id, so a change to the inner item alone sends nothing; `FindItem` returns the first, so option (i)'s key path runs the outer item's handler once. |
| `CompositeRootContext.cs` | The registry the root part cascades with `IsFixed` inside its element (ADR 16 rule 9, BLZX2001). Items `Register`, `Unregister`, report `RegistrationChanged` and `ElementReplaced`, and ask for `FlushAsync`. `Require` throws the error of an item outside a root (CMP-STR-02, CMP-EDGE-01, internal guards). |
| `CompositeItemBehavior.cs` | One item's mechanism. Given the part's own `onkeydown` handler, it declines the consumer's and runs it from that handler with the one-shot marker, and the root runs it for a key it handles (option (i) of ADR 04's note of 2026-10-22, chosen by the user 2026-10-23). It registers the id its part renders (the generated id, or the consumer's) with the consumer's `tabindex`, in the batch that creates the part, and unregisters on dispose. `AddAttributes` writes `tabindex="-1"` on every render: the initial value under the handover, unchanged afterwards, so Blazor never writes it again, while the consumer's value wins in the merge. After render it asks the root to send what changed, and reports a new element under the same id. |
| `CompositeItemBehavior.cs`, M3 (track 1) | `SetRegistration(id, attributes, disabled = false, focusableWhenDisabled = false)` (E3): the item's flags travel in its registration, compared on every parameter set, so a change sends one `update`; RadioRoot's two-argument call is unchanged. |
| `CompositeListBehavior.cs` (M3, track 1, E1) | One registration-only list's mechanism (TabsRoot's panels, AccordionRoot's items; CMP-STR-03), composed into the list root part. It attaches the one `CompositeTwin` with `RegistrationOnly` as the root does: by `Element`, the generated id or a late id. It sends one `update` per batch that changed the ids or an element, and sets each item's index from the module's order report (its position, or -1 when the report does not name it), raising `ItemsChanged` once per report. The module installs no listener, writes no `tabindex` and keeps no highlight for it. |
| `CompositeListContext.cs` (M3, track 1, E1) | The registry the list part cascades with `IsFixed`, separate from `CompositeRootContext`: a composite item never registers with a list, a list item never with a root, and a Toggle inside a TabsPanel does not infer composite mode (design point 6). |
| `CompositeListItemBehavior.cs` (M3, track 1, E1) | One list item's mechanism (TabsPanel, AccordionItem). It registers the id its part renders (every list item renders one, design point 2) and renders nothing of its own, no `tabindex` and no handler. `Index` is -1 until the first report and in prerender (CMP-STA-15), then the reported position, and the part re-renders only when it changes (ADR 16 rule 8). Without a list it is inert: index -1, nothing registered, a dispose that does not throw. |
| `CompositeLiterals.cs` | `Orientation?` → `horizontal`, `vertical`, `both` (`null`); `TextDirection` → `ltr`, `rtl`. |
| `CompositeAttributes.cs` | `ActiveItem = "data-composite-item-active"` (CMP §6.11): the attribute Radio (RAD-DOM-02) and Tabs write on the item that takes the initial tab stop. |

Removal-only batches: a batch that only removes items runs no item's after-render. The item's dispose therefore makes the root render, unless the root already rendered in that batch, and the root's after-render sends the one `update`. L2 proves both paths (`CompositeRootTests`: the nested unmount, and a parent removing an item).

What JavaScript owns (not here): the item order and move detection, the highlighted index and its publication adjustments, the key resolution, the focus moves, the roving `tabindex` from attach, the pending-navigation flag and the focus-driven selection, the leaving blur.

## Human check

- No internal component instance: the behaviours are composed into the parts, and the cascade is the only component the root adds (ADR 16 rule 10).
- One `update` per render batch: a render that changes nothing sends nothing, and the options are compared field by field before a record is built (ADR 16 rule 7; `CompositeAllocationBudgetTests` only tightens on the library's share; M3 track 1 raised it 8 bytes per public property the test host gained, the harness's own cost, each noted in the test).
- JavaScript owns every item's `tabindex` after attach: C# renders `-1` and never another value, and no C# code mirrors the highlighted index into an attribute. An item of a registration-only list renders no `tabindex` at all, and the module writes none.
- One registration per id reaches the module, the first (the outer item's); values (a Tab's `value`) never cross to JavaScript, only ids and the two flags.
